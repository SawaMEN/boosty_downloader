1. [ ] **P0.** Публикация готовых бинарников и Ubuntu CI для установки одной командой **пройдены**. Остались проверка чистой Debian и выпуск стабильного `vX.Y.Z`.

3. [ ] **P0.** Проверки имитации аварий Native и Docker **пройдены в CI**: откат, `/healthz`, архивный файл, конфигурация и TLS. Остались реальный VPS, автоматический install-update и аварии на уровне диска.
4. [ ] **P0.** Защита открытия файлов и отрицательные тесты доступа **реализованы**: HTML, ZIP, медиа, HTTP Range, версии, симлинки и специальные файлы. Остались E2E восстановления, удаления и временных файлов на реальных архивах.
5. [ ] **P1.** Опциональная синхронизация SQL-индекса истории/медиа добавлена в коде (`BD_SQLITE_MEDIA_SHADOW=1`), но ещё нужны подтверждение полного CI, нагрузочные/аварийные испытания и гарантированный cutover; JSON и ACL остаются основными.
6. [ ] **P1.** Безопасное переключение JSON → SQLite и обратно с блокировкой конкурентных записей, резервным снимком и испытаниями аварий.
7. [ ] **P1.** Улучшить поддержку сложных HLS/DASH, неполных комментариев и точность форматирования HTML. DASH `SegmentTimeline S@r=-1` для конечных VOD добавлен. Комментарии теперь проверяются по признакам неполной выдачи, включая скрытые ответы и удалённые записи; HTML группирует Draft.js текстовые фрагменты и сохраняет переносы строк. Живые тесты API, вложенная пагинация всех ответов и сложные форматы пока остаются; жирный и курсив выводятся безопасными HTML-тегами, глубина комментариев и число элементов ограничены одинаково для API и офлайн-архива, неизвестные блоки явно помечаются как неподдерживаемые.
8. [ ] **P2.** Автоматические браузерные E2E для входа/выхода, авторизации, предпросмотра, комментариев, каталога, XSS и мобильной навигации добавлены в CI (Chromium на изолированном HTTPS-сервере). Остались нагрузочные тесты больших архивов, дополнительные браузерные сценарии и документация релиза 1.0.

- [x] Проверки браузерного входа, скрытия панели до авторизации, навигации, выхода, серверного отзыва сессии и мобильного меню.
- [x] Проверки на XSS и раскрытие исходных данных в предпросмотре поста, вложенных комментариях и карточках каталога. Внешние ответы Boosty заменены детерминированными сетевыми фикстурами; аутентификация, TLS, API, DOM и JavaScript работают на настоящем сервере.
- [ ] Дополнить сценариями загрузок архивов, восстановления и обмена файлами на настоящем браузере; отдельно провести испытания с реальными публикациями Boosty и на VPS.

Локальный запуск на Linux: собрать `go build -o /tmp/boosty-browser-e2e ./cmd/boosty-downloader`, установить `python -m pip install playwright==1.57.0` и `python -m playwright install chromium`, затем `BOOSTY_E2E_BIN=/tmp/boosty-browser-e2e python tests/browser_e2e.py`. Для системного Chromium можно задать `BOOSTY_E2E_CHROMIUM=/usr/bin/chromium`.

## Офлайн-ограничения и неизвестные блоки (14.11.2026)

- [x] Общий **нерекурсивный обход** дерева комментариев в API и архиве с предельной глубиной **64 уровня** и не более **10 000 узлов**. При превышении пределов архив получает частичный статус, вместо ложно полного; оригинальный ответ Boosty сохраняется отдельно.
- [x] Живой предпросмотр больше не обрывает вложенные ответы после 15 уровней и не раскрывает текст удалённых комментариев. Офлайн-HTML и API используют одинаковый порядок дочерних записей.
- [x] Неизвестные и повреждённые блоки не исчезают бесследно: на их месте отображается нейтральное предупреждение, архив помечается частичным, а содержимое остаётся в локальном `post.json`. Хеш исходного блока участвует в отпечатке версии, но не раскрывает содержимое через HTML/API.
- [x] Автоматические тесты дерева (большая глубина и ширина, удалённые родители, точные пределы), порядка блоков, XSS/URL-утечек и сохранения разных версий неподдерживаемого содержимого.

## SQLite: этап 12.3

- [x] **12.3.1** — офлайн JSON → SQLite, схема v1, тесты.
- [x] **12.3.2** — проверка целостности, владельцев, ACL и файлов; CLI `boosty-dbcheck`.
- [ ] **12.3.3** — транзакционный SQL-репозиторий реализован отдельно, но не включён в основной Storage и ещё требует интеграции.
- [ ] **12.3.4** — подготовительный мост: **4 из 6**, **2 осталось**.

Добавлено отдельное безопасное восстановление полного снимка **только в новый каталог**: `boosty-dbcheck --restore-full-snapshot-dir SNAPSHOT --restore-to NEW-PATH`. Сохранённые SHA-256 проверяются до и после копирования, каждый путь открывается без перехода по симлинкам, а атомарная публикация через Linux `renameat2(RENAME_NOREPLACE)` не может перезаписать действующий каталог. Добавлены тесты повреждений, гонки с созданием назначения, ошибки ENOSPC и реального `SIGKILL` до публикации. **Автоматического переключения работающей установки на восстановленный каталог нет.**

Добавлена самостоятельная офлайн-копия **всего каталога данных**, включая архивы, историю, CAS, аккаунты и находящиеся в каталоге секреты: `boosty-dbcheck --full-snapshot-dir` и независимое `--verify-full-snapshot-dir`. Проверяются приватность, полный перечень путей, SHA-256 всех файлов, запрет симлинков/специальных файлов, незавершённых транзакций и конкурентного сервера. **Это не копия всего VPS:** конфигурация из `/etc`, внешние TLS-ключи и бинарники требуют отдельного backup; автоматический restore полного дерева ещё не реализован.

Добавлено офлайн-восстановление только неавторитетного SQLite Shadow из проверенного резервного снимка с атомарной заменой SQL, сверкой JSON/ACL и медиа, отказом при изменении данных, проверками блокировок и тестами восстановления. Новые Linux E2E-испытания в отдельных процессах используют `SIGKILL` при частичной записи, после подготовки и после подмены SQL, а также программно моделируют `ENOSPC` до/после подмены. Проверяются неизменность JSON, повторный запуск и удаление временных файлов после успешного восстановления. Для проверки реального системного `ENOSPC` добавлен отдельный CI job с изолированным Linux tmpfs 32 МиБ: он проверяет отказ на настоящем заполненном разделе, отсутствие повреждения базы и повторную операцию после освобождения места. **Отключение питания, переполнение диска самого VPS и SQL-primary ещё не проверены; полное восстановление данных не реализовано.**

Устранён узкий промежуток между проверкой резервной копии и фиксацией хеша SQL. Теперь исходные SHA-256 и размер SQLite фиксируются из манифеста **до** верификации, отдельно фиксируется хеш самого манифеста; изменения после верификации (в том числе с согласованным пересчётом манифеста), аудита или staging блокируют восстановление. Добавлены негативные тесты этих случаев. Проверки не делают резервную копию неизменяемой: все сторонние писатели должны быть остановлены.

Дополнительно внедрена системная блокировка каталога данных для предотвращения запуска второго сервера и офлайн-операций при активном сервере (включая сброс пароля). Это защита от конкурирующих процессов проекта, а не замена остановки сторонних писателей файлов.

В 12.3.4 уже присутствуют журнал восстановления `jobs.json` + `imports.json`, проверяемый бэкап метаданных, необязательное JSON → SQLite Shadow, офлайн-индексация медиа с SHA-256 и экспериментальный фоновый индекс файлов (`BD_SQLITE_MEDIA_SHADOW=1`) с повторной сверкой, задержкой на активные загрузки и транзакционным SQL-обновлением. Добавлены отменяемое контекстом SHA-256-сканирование, запрет проигрывания устаревших журналов JSON поверх новых прав и строгий офлайн-гейт `boosty-dbcheck --cutover-preflight --recovery-dir`, сравнивающий всю доступную SQL/JSON/медиа-метаинформацию с проверенной копией. Проверка не выполняет cutover. **Рабочая база остаётся JSON**; реальный SQL cutover и аварийные E2E пока не выполнены.

## Критерии стабильного релиза

- CI проходит: Go + race detector, UI-проверки, Docker, amd64/arm64 и обе установки.
- Бинарники опубликованы в GitHub Releases с `SHA256SUMS`.
- HTTPS и система аккаунтов проверены; ни один пользователь не получает доступ к чужим данным.
- Живые публикации Boosty архивируются без ложных статусов «полностью сохранено».
- Резервное копирование, обновление и откат проверены на копии VPS.
