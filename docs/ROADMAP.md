## SQLite: этап 12.3

- [x] **12.3.1** — офлайн JSON → SQLite, схема v1, тесты.
- [x] **12.3.2** — проверка целостности, владельцев, ACL и файлов; CLI `boosty-dbcheck`.
- [ ] **12.3.3** — начата интеграция с рабочим HTTP-сервером: опциональные SQL-индексы каталога и списков архивов уже используются через JSON-проверку ACL; основной SQL-репозиторий записей и cutover ещё не включены.
- [ ] **12.3.4** — подготовительный мост: **4 из 6**, **2 осталось**.

Добавлено отдельное безопасное восстановление полного снимка **только в новый каталог**: `boosty-dbcheck --restore-full-snapshot-dir SNAPSHOT --restore-to NEW-PATH`. Сохранённые SHA-256 проверяются до и после копирования, каждый путь открывается без перехода по симлинкам, а атомарная публикация через Linux `renameat2(RENAME_NOREPLACE)` не может перезаписать действующий каталог. Добавлены тесты повреждений, гонки с созданием назначения, ошибки ENOSPC и реального `SIGKILL` до публикации. **Автоматического переключения работающей установки на восстановленный каталог нет.**

Добавлена самостоятельная офлайн-копия **всего каталога данных**, включая архивы, историю, CAS, аккаунты и находящиеся в каталоге секреты: `boosty-dbcheck --full-snapshot-dir` и независимое `--verify-full-snapshot-dir`. Проверяются приватность, полный перечень путей, SHA-256 всех файлов, запрет симлинков/специальных файлов, незавершённых транзакций и конкурентного сервера. **Это не копия всего VPS:** конфигурация из `/etc`, внешние TLS-ключи и бинарники требуют отдельного backup; автоматический restore полного дерева ещё не реализован.

Добавлено офлайн-восстановление только неавторитетного SQLite Shadow из проверенного резервного снимка с атомарной заменой SQL, сверкой JSON/ACL и медиа, отказом при изменении данных, проверками блокировок и тестами восстановления. Новые Linux E2E-испытания в отдельных процессах используют `SIGKILL` при частичной записи, после подготовки и после подмены SQL, а также программно моделируют `ENOSPC` до/после подмены. Проверяются неизменность JSON, повторный запуск и удаление временных файлов после успешного восстановления. Для проверки реального системного `ENOSPC` добавлен отдельный CI job с изолированным Linux tmpfs 32 МиБ: он проверяет отказ на настоящем заполненном разделе, отсутствие повреждения базы и повторную операцию после освобождения места. **Отключение питания, переполнение диска самого VPS и SQL-primary ещё не проверены; полное восстановление данных не реализовано.**

Устранён узкий промежуток между проверкой резервной копии и фиксацией хеша SQL. Теперь исходные SHA-256 и размер SQLite фиксируются из манифеста **до** верификации, отдельно фиксируется хеш самого манифеста; изменения после верификации (в том числе с согласованным пересчётом манифеста), аудита или staging блокируют восстановление. Добавлены негативные тесты этих случаев. Проверки не делают резервную копию неизменяемой: все сторонние писатели должны быть остановлены.

Дополнительно внедрена системная блокировка каталога данных для предотвращения запуска второго сервера и офлайн-операций при активном сервере (включая сброс пароля). Это защита от конкурирующих процессов проекта, а не замена остановки сторонних писателей файлов.

В 12.3.4 уже присутствуют журнал восстановления `jobs.json` + `imports.json`, проверяемый бэкап метаданных, необязательное JSON → SQLite Shadow, офлайн-индексация медиа с SHA-256 и экспериментальный фоновый индекс файлов (`BD_SQLITE_MEDIA_SHADOW=1`) с повторной сверкой, задержкой на активные загрузки и транзакционным SQL-обновлением. Добавлены отменяемое контекстом SHA-256-сканирование, запрет проигрывания устаревших журналов JSON поверх новых прав и строгий офлайн-гейт `boosty-dbcheck --cutover-preflight --recovery-dir`, сравнивающий всю доступную SQL/JSON/медиа-метаинформацию с проверенной копией. Проверка не выполняет cutover. **Рабочая база остаётся JSON**; реальный SQL cutover и аварийные E2E пока не выполнены.

## Целостность ZIP при конкурентных изменениях (16.11.2026)

- [x] ZIP-передача проверяет сохранённый SHA-256 **по тем же байтам, которые копирует в архив**, без дополнительного прочтения многогигабайтного медиа. При повреждении с неизменным размером поток прерывается до записи центрального каталога ZIP. После начала передачи HTTP-статус уже может быть `200`, но такой файл **не является корректным ZIP**.
- [x] Неисправимый SHA-256 в манифесте и противоречащие друг другу хеши одного имени отвергаются заранее с HTTP 409; продолжается контроль размера во время копирования.

- [x] Добавлены тесты новых SQL-записей, сохранения секретов и медиа, повреждённого источника, несовместимых учётных данных, `ENOSPC`, гонки назначения и `SIGKILL` до публикации.
- [ ] **Остаётся:** реальный SQL-primary Storage и атомарное включение/отключение на работающем сервере с журналом и без потери данных, проверка на настоящих публикациях Boosty и VPS. Отдельное восстановление не является production rollback.

## SQL 12.3.5 — транзакционный SQL-first журнал и восстановление после сбоя (23.11.2026)

- [x] Реализован внутренний `sqlitePrimaryCommitMetadata`: проверка исходного JSON/SQL, приватный fsync-журнал с контрольными суммами и двумя поколениями задач/импорта, одна SQL-транзакция обновления задач/ACL/импорта, затем crash-safe зеркальный двухфайловый JSON-коммит.
- [x] На старте сервера, до аккаунтов, HTTP и фоновых задач, `recoverSQLitePrimaryCommitLocked` проверяет SQL на полное соответствие исходному или новому состоянию журнала. Неуспевший SQL-коммит отменяет intent без записи, зафиксированный SQL-коммит **докатывает JSON вперёд**. Неизвестные состояния, повреждения ACL или журнала блокируют запуск без предположений.
- [x] Проверка незакрытого SQL-primary журнала встроена в офлайн-снимки и экспорт. После `SIGKILL` SQLite сам восстанавливает WAL; предварительная проверка отсутствия WAL не мешает запуску recovery.
- [x] Добавлены тесты коммита и ACL, несовпадений SQL/JSON, `ENOSPC` и реальных `SIGKILL` в фазах `prepared`, `sql-committed` и `json-committed`.
- [ ] Этот компонент **пока не подключён к каждому пути записи `Storage`** и не допускает включения `BD_SQLITE_PRIMARY=1`. Для активного SQL-primary остаются маршрутизация всех писателей и фоновых операций, durable backend-selection, аварийный rollback и VPS E2E. Основной статус — 7 из 13 крупных этапов.

## SQL 12.3.6 — единый адаптер записей Storage (23.11.2026)

- [x] Три существующих метода сохранения `Storage` — `saveJobsLocked`, `saveImportsLocked` и `saveJobsImportsLocked` — направляют изменения в общий SQL-first адаптер, **если он внутренне установлен**. Это покрывает записи задач, импорта, ACL и совместных изменений расписания без второго набора HTTP-обработчиков.
- [x] Адаптер использует проверенный SQL-first журнал: SQLite-коммит первым, затем JSON-зеркало. После ошибки повторно проверяет восстановление и содержимое обоих хранилищ: если новое состояние действительно зафиксировано, завершает операцию успешно, иначе отдаёт ошибку вызывающему коду.
- [x] При неустранимой ошибке SQL/JSON адаптер переводится в состояние quarantine; новые записи запрещены, а основные пути чтения задач и импорта не возвращают потенциально устаревшие данные. Одновременная работа SQL-first с JSON shadow запрещена.
- [x] Добавлены интеграционные Go-тесты на задачи, выдачу прав, импорт, отмену, совместный автоимпорт и отказ при повреждённом SQL; штатный `BD_SQLITE_PRIMARY=1` по-прежнему отклоняется.
- [ ] **Режим для production остаётся закрытым**: необходимы полная проверка всех чтений/файловых операций, атомарный персистентный выбор backend, стратегия отката с SQL-only данными и тесты на живом VPS. Это не завершает крупный этап SQL-primary. Общий счёт: **7 из 13**, осталось **6**.

## SQL 12.3.7 — внутреннее SQL-чтение и постоянный выбор backend (23.11.2026)

- [x] Для внутреннего SQL-first адаптера реализован полный транзакционный снимок SQLite задач, импортов и выдач доступа (`sqlitePrimaryReadSnapshotLocked`). Проверяются все строки/индексы, ACL, владелец, отсутствие потерянных через JOIN архивов и целостность синхронизированного поколения в памяти; **чтение не переключается на JSON при ошибке SQLite**.
- [x] Внутренние `Storage.get`, `all`, `queued`, `importsFor`, `queuedImports`, `importCanceled` при установленном `Storage.primary` используют SQL-снимки. Расхождение или поломка приводит к блокировке чтений и записи, а не к выдаче устаревших разрешений.
- [x] Добавлены проверки реальных SQL-чтений, владельцев, очередей, поддельных ACL, изменённых индексных полей, отсутствующих и новых SQL-only архивов, неисправной базы и несовпадения памяти. Сохранён JSON-режим по умолчанию.
- [x] Введён строгий приватный `.metadata-backend.json` (версия 1): неявное отсутствие означает JSON. `boosty-dbcheck --data-dir DATA --pin-json-backend` атомарно и с `fsync` фиксирует JSON как активный backend только на остановленном хранилище. Повторная команда не переписывает корректный маркер.
- [x] Сервер и автономный `newStorage` **до любого JSON-журнала** запрещают запуск с повреждённым, неизвестным или SQL-active маркером; переменная `BD_SQLITE_PRIMARY=1` по-прежнему запрещена. Устранён обход валидации аргументов у `--restore-sqlite-json-dir`.
- [ ] **Остаётся до рабочего SQL-primary:** производительные точечные и пакетные SQL-чтения (текущий проверочный снимок O(N)), атомарная установка active=sqlite только после полного offline preflight и recovery point, полная проверка работников/медиа/политик, обратный rollback после SQL-only операций и реальные VPS+Boosty испытания. Большие этапы: **7 из 13**, осталось **6**. Этот подэтап сам по себе **не включает** SQL-primary.
