# Сжатие и экономия диска в Boosty Downloader

Дата решения: 10.11.2026. Это описание реально внедрённого первого слоя хранения и оставшейся дорожной карты. Не является обещанием конкретного процента экономии: результаты зависят от состава публикаций.

## Сравнение алгоритмов

| Метод | Плюсы | Минусы | Решение |
|---|---|---|---|
| **Zstandard (Zstd)** | Высокая скорость сжатия и распаковки, уровни 1–19, возможность словарей | Требует кодек; медиаданные обычно уже сжаты | **Основной режим** для приватных оригинальных JSON |
| Brotli | Хорошо для HTML/CSS/JS и статического веб-контента | Медленные высокие уровни; не решает проблему видео | Рассмотреть для HTTP-ответов и статических ресурсов |
| LZMA2 | Сильное сжатие, 7z, solid archives | Выше требования к CPU/RAM, неудобно для постоянного чтения отдельных файлов | Опциональный экспорт/холодное хранение |
| PPMd | Подходит некоторым текстовым корпусам | Память, скорость, зависимость от типа текста | Не использовать как основной |
| LZ4 | Очень быстрая распаковка | Обычно слабее по размеру | Возможный кеш, не долгосрочный архив |
| Fast LZMA2 | Оптимизация LZMA2 из проекта 7-Zip ZS | Не универсальный контейнер хранения для Go-сервиса | Не нужен для MVP |
| Lizard/LZ5 | Дополнительные методы из 7-Zip ZS | Ограниченная распространённость | Не выбирать по умолчанию |
| gzip/Deflate | Совместимы с ZIP и браузерами | Часто медленнее Zstd при близком сжатии | ZIP-экспорт остаётся совместимым |

Референсный бенчмарк автора Zstd (Silesia, i7-9700K) для быстрых уровней: Zstd -1 — 2.896× и 510 MB/s на сжатие; Brotli -1 — 2.883× и 290 MB/s; zlib -1 — 2.743× и 105 MB/s; LZ4 — 2.101× и 675 MB/s. Это **не замеры Boosty Downloader и не прогноз реальной экономии**: https://github.com/facebook/zstd .

Официальный 7-Zip использует LZMA2 как основной метод 7z; форк **7-Zip ZS** дополнительно предлагает Zstd, Brotli, LZ4 и Fast LZMA2. Копирование кода 7-Zip не требуется. Источники:
- https://www.7-zip.org/7z.html
- https://github.com/ip7z/7zip/blob/main/C/Lzma2Enc.c
- https://github.com/ip7z/7zip/blob/main/DOC/License.txt
- https://7-zip-zstd.com/methods.html
- https://github.com/facebook/zstd/blob/dev/programs/zstd.1.md
- https://github.com/facebook/zstd/blob/dev/contrib/seekable_format/README.md

## Реализовано: сжатие при сохранении

- Приватные исходные `post.json`, `comments.json`, `comments-raw.json` сжимаются Zstandard **при записи снимка**. Расширение сжатых данных — `.json.zst`.
- Файл сначала записывается атомарно. При успехе удаляется альтернативная, несжатая версия того же файла: обе версии одновременно не хранятся. Если Zstd даёт менее 5% экономии или JSON короче 2 КБ — сохраняется обычный JSON без лишних затрат.
- Используется системный `zstd` с одним потоком (`-T1`), установленный установщиком native и в Docker-образе. При отдельном запуске бинарника без системного `zstd` метаданные сохраняются в читаемом JSON.
- В админ-панели доступны уровни 0 (выключено), 1, 3 (по умолчанию), 9, 15; сервер дополнительно проверяет диапазон 0–19. Настройка сохраняется между перезапусками. Изменение уровня действует на **новые/обновлённые** снимки, без массовой перезаписи старых архивов.
- Манифест `manifest.json` и `index.html` остаются несжатыми. Поэтому архив открывается в обычном браузере, а комментарии/видео/вложения доступны без отдельного этапа распаковки. Сырые JSON никогда не выдаются в публичном ZIP или общих архивах: они могут содержать подписанные CDN-URL и другие непубличные метаданные.
- ZIP-экспорт по-прежнему использует стандартный Deflate и сохраняет совместимость с обычными архиваторами.

## Реализовано: дедупликация медиа по SHA-256

- Каждое скачивание проходит контроль SHA-256, а одинаковые медиа могут использовать **один физический объект** в `<dataDir>/blobs/sha256/<2 символа>/<sha256>`.
- У каждого поста остаётся обычный путь `media/<file>` с hard link. Это сохраняет мгновенный просмотр, перемотку HTTP Range, отдельный ZIP и корректные права на уровне веб-приложения.
- Нельзя подменить чужой файл через символическую ссылку: используются только regular files, SHA-256, проверка размера и атомарная замена. Базовые файлы переводятся в режим только для чтения, все изменения загружаются в новые `.part` и атомарно замещают ссылку.
- Если файловая система не поддерживает hardlink, файл остаётся отдельно. Дедупликация даёт экономию только для **идентичных байтов** (не для одного видео в двух разных разрешениях).
- При удалении последней копии общий объект освобождается. При обновлении видео неиспользуемый прежний объект проверяется для удаления. Настройку дедупликации включает и отключает администратор.
- Доступность чужой копии не следует из хранения общих байтов: HTTP-пути, ZIP и каталог общих архивов по-прежнему проверяют владельца и разрешения. Дедупликация не означает публичное распространение.

## Чего ещё нет

- Видео **не перекодируются** автоматически. Их повторная компрессия архиваторами неэффективна и мешает просмотру с перемоткой. Опциональное перекодирование AV1/HEVC с заданным качеством, лимитом CPU/RAM и обязательным сохранением исходника до подтверждения требуется отдельно.
- Миграция старого содержимого и пакетная дедупликация существующих архивов отсутствуют: старые файлы могут перейти на новую схему после очередного обновления снимка.
- Пока нет пользовательских квот по объёму/трафику, оценки свободного диска, панели физических/логических размеров, периодического сканирования orphan-файлов и изолированного восстановления «холодных» 7z-архивов.
- Zstd dictionary training для множества малых JSON и Zstd seekable frames рассматриваются как дополнительная оптимизация. Для MP4, работающего с HTTP Range, seekable Zstd не заменяет обычный потоковый видеофайл.
- Нет замеров с настоящими медиа из Boosty и нагрузки на конкретном VPS. Без таких замеров обещать сокращение «в сотни раз» нельзя.

## Критерии приемки следующего этапа

1. Тесты без потерь: побайтное восстановление JSON из `.zst`, старый `.json` и переключение настройки.
2. Две копии одного видео используют один inode, удаление первой сохраняет вторую, удаление последней освобождает blob.
3. Дедупликация не обходит разграничение прав, ZIP и локальный HTML продолжают работать.
4. Утечка токенов из `.json.zst`, raw API и ZIP исключена серверной ACL и фильтрацией файлов.
5. Реальные бенчмарки на VPS: физический объём, логический объём, время загрузки/просмотра, RAM/CPU по типам медиа.
6. Настроить квоты и безопасную миграцию старых архивов, сохранить rollback/backup перед миграцией.
