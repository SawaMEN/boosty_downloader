# Проверка, установка и откат обновлений панели

**Взято как архитектурный подход:** `SRC-WP-06` — WordPress `src/wp-admin/includes/class-core-upgrader.php` (проверки, блокировка, резервная версия и rollback); `SRC-IMM-01/05` — выделенные фоновые операции, отсутствие доступа веб-процесса к системным привилегиям. Реализация написана самостоятельно на Bash/Go для Linux.

## Как это работает

1. Администратор выбирает канал `stable` (по умолчанию) или `dev`, интервал проверки 1–168 часов и отдельно разрешает/запрещает **автоматическое применение** (по умолчанию выключено).
2. Хостовый `systemd`-таймер `boosty-downloader-update.timer` запускает `/usr/local/bin/bdy-auto-update` примерно раз в час. Скрипт учитывает интервал и запоминает дату проверки.
3. **Публичные стабильные релизы** загружаются анонимно через GitHub HTTPS: ни `gh`, ни токен GitHub на VPS не требуются. Для **dev-артефактов CI** нужен `gh auth login` от root (или смените канал на stable). Токен не передаётся веб-процессу и Docker-контейнеру.
4. Канал `stable` использует последний опубликованный релиз GitHub с корректным тегом `vX.Y.Z`; канал `dev` — последнюю успешную сборку GitHub Actions ветки `main`. Dev-канал может быть нестабильным, автоматическое применение включается только по решению администратора.
5. **Native/systemd:** загружается бинарник для архитектуры AMD64/ARM64, сравнивается SHA-256 из набора релиза/CI, сохраняется предыдущая версия, выполняется атомарная замена, перезапуск и проверка локального `/healthz`. Если проверка не пройдена, предыдущий бинарник возвращается.
6. **Docker:** из соответствующего релизного тега или успешного коммита извлекается только исходный код приложения. Сохраняются предыдущий каталог проекта и образ Docker, выполняется сборка нового образа и проверка `/healthz`. При ошибке откатываются образ и исходники. Секреты в `/etc/boosty-downloader/environment` и пользовательские данные в `/var/lib/boosty-downloader` не заменяются.
7. Информацию последней проверки root сохраняет в `update-status.json` в каталоге данных. Веб-интерфейс только **читает** этот файл через `GET /api/admin/updates`; никто, кроме администратора, не видит журнал и не может менять политику.

## Управление

- Панель администратора → «Обновления»: канал, период, автоустановка и статус (все значения сохраняются в `accounts.json`).
- `sudo bdy update` — проверить сейчас, применить только если автообновление разрешено настройкой.
- `sudo bdy update --apply` — проверить и применить вручную с полномочиями владельца VPS, даже если автоустановка отключена.
- `sudo bdy rollback` — восстановить предыдущий бинарник либо Docker-образ и код проекта (только на сервере).
- `sudo systemctl status boosty-downloader-update.timer` и `sudo journalctl -u boosty-downloader-update.service` — диагностика.

**Примечание:** `gh` и авторизация нужны только для dev-канала GitHub Actions. Не вставляйте ключ GitHub в веб-панель. Если в публичном репозитории ещё нет стабильного релиза, канал `stable` показывает «релиз недоступен», а не устанавливает случайный коммит `main`. SHA-256 защищает от случайной порчи файла, но не заменяет проверку доверия к репозиторию и релизу. Для строгой цепочки доверия нужны подписи артефактов.

## Ограничения до релиза 1.0

- [ ] Проверить фактические обновления и откаты на реальном VPS для native и Docker при ошибке старта, прерывании питания и потере сети.
- [ ] Добавить атомарные миграции и резервное копирование метаданных хранилища перед несовместимым обновлением схемы. Текущие релизы не должны менять формат данных несовместимым способом без мигратора.
- [ ] Подписывать релизы и проверять независимые сигнатуры, не полагаясь только на GitHub и SHA-256.
- [ ] Проверить управление обновлениями при нестандартных systemd-окружениях, SELinux/AppArmor и различных Linux-дистрибутивах.
