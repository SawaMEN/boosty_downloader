# Boosty Downloader Web — техническая аналитика и карта разработки

Дата анализа: 10.11.2026. Версия документа: 1.2. Статус: исследование завершено, реализация не начата.

## 1. Цель и границы

Разработать самодостаточное веб-приложение для установки на собственный Linux VDS/VPS. Через веб-интерфейс пользователь вставляет ссылку Boosty, видит метаданные и список видео, выбирает разрешение и способ выдачи: (A) скачать в браузер на ПК, без постоянного сохранения на VPS; (B) сохранить в медиатеке VPS и при необходимости забрать файлы позже. Третий основной режим — архивировать целиком один пост на VPS, чтобы позже открыть его сохранённую копию через защищённую веб-панель. Опционально включать комментарии с ответами и прикреплённые файлы. Предусмотреть экспорт переносимого ZIP с автономной HTML-копией; массовая синхронизация блога — в более позднем релизе.

**Принципиальные ограничения:** доступ к закрытому материалу возможен только при действующем праве просмотра через пользовательский аккаунт Boosty. Продукт не снимает DRM, не обходит платную подписку и не предназначен для распространения чужого материала. Программная авторизация панели и авторизация Boosty — две разные системы.

### Сценарии (user stories)

1. Публичное видео: вставить ссылку → проверка → увидеть доступные форматы → скачать на ПК.
2. Закрытое видео с действующей подпиской: подключить Boosty-профиль → проверить доступ → скачать.
3. Передача сразу на ПК: запрос данных идёт через VPS, байты отправляются браузеру потоком. При обычном MP4 долговременное хранение не требуется.
4. Сохранить на VPS: задача помещается в очередь, может продолжаться после закрытия браузера, доступна в медиатеке с возможностью удаления.
5. В посте несколько роликов: показывать каждый отдельно, не путать ID видео с ID поста, корректно выбирать конкретный ролик.
6. При обрыве загрузки на VPS: при следующем запуске продолжить при поддержке HTTP Range и валидности того же медиаобъекта.
7. Истёк токен: обновить без потери состояния, либо показать понятное действие «Переподключить аккаунт».
8. Архив публикации: вставить ссылку → выбрать «Архивировать пост» → сохранить оформление, текст, изображения, видео/аудио (если включены), метаданные и доступные вложения → открыть локальную страницу `/library/posts/{id}` позднее.
9. Комментарии: отдельный флажок «Комментарии и ответы»; архивировать авторов, даты, структуру веток, текст и медиа внутри комментариев; сообщать об ограничениях API, когда не удалось получить все ответы.
10. Вложения: отдельный флажок «Прикреплённые файлы»; включить файлы в архив по желанию; в режиме без вложений сохранять их названия и явно показывать «файл не включён», а не сломанную ссылку.
11. Перенос архива: экспорт `ZIP` с `index.html`, `manifest.json` и локальными ресурсами; без зависимости от работающего VPS/Boosty при открытии внутри другой машины, если все нужные ресурсы действительно сохранены.
12. Запуск по IP или домену: поддержать оба варианта установки, но токены разрешить вводить только поверх защищённого соединения.

## 3. Архитектурное решение

**Рекомендуется: собственный Go web backend (стандартный `net/http` либо chi) + React/Vite frontend + SQLite WAL + systemd, без Docker.** Использовать алгоритмы и тестовые сценарии `b00p` в MIT-совместимом виде, проверить их лицензирование и pin зависимостей. `ath31st` не форкать целиком: Tauri-код под VPS не нужен. `yt-dlp` + `ffmpeg` — только подключаемый локальный исполнитель для HLS/DASH и внешних видео.

Почему Go: один компактный Linux-бинарник, простая установка и восстановление через systemd, невысокие накладные расходы на типичных VPS, удобный потоковый HTTP и проверенный пример b00p. Альтернатива — Rust/Axum + `boosty_api_rs` — технически допустима, но для этой задачи требует переноса/реализации очереди, Range-докачки и веб-сервера, что добавляет работу. Оптимальное техническое решение не означает, что весь Go-код `b00p` можно автоматически применять без тестирования.

```
Браузер (ПК / телефон)
    │ HTTPS + cookie сессии панели
    ▼
Caddy/Nginx (TLS, reverse proxy, лимиты)
    ▼
Go web app: HTTP API + встроенный frontend
    ├── Auth панели (администратор)
    ├── Boosty connector (access/refresh, API, список медиа)
    ├── Media resolver (MP4, HLS, DASH, внешние embeds)
    ├── Transfer service
    │     ├── Stream-to-browser (без долговременного файла)
    │     └── Queue → Download workers → /var/lib/boosty-web/media
    ├── Post Archive Builder
    │     ├── Нормализованный snapshot + raw API payload (с удалёнными секретами)
    │     ├── Дерево комментариев и вложенные медиа (опционально)
    │     ├── Локальные ресурсы + безопасный HTML renderer
    │     └── Проверка полноты + экспорт переносимого ZIP
    ├── Protected archive viewer: /library/posts/{id}
    ├── Task state + metadata: SQLite WAL
    └── Optional ffmpeg / yt-dlp sandbox
```

### Разделение процессов

- Один пользователь `boosty-web` без sudo и root-доступа.
- Основное приложение и Go-воркеры могут работать в одном бинарнике на первом этапе; задачи и состояние хранятся в БД для восстановления после рестарта.
- Внешние `ffmpeg` и `yt-dlp` изолированы, ограничены по CPU/RAM и времени; автоматические загрузки из интернета или запуск скриптов с параметрами, взятыми из URL, запрещены.
- Для нескольких пользователей — отдельные Boosty-секреты, отдельные ACL/каталоги; первый выпуск — **single-admin**, что сильно упрощает модель угроз.

## 4. Три режима выдачи и реальное поведение

### A. «Сразу на ПК»

1. Браузер отправляет ссылку и выбранный video ID в API. 2. Сервер получает актуальную ссылку на медиа, применяя **свою** учётную запись Boosty. 3. HTTP-ответ передаётся браузеру по частям с `Content-Disposition: attachment` и корректной кодировкой имени. 4. Сервер использует backpressure, таймауты и разрывает соединение после закрытия вкладки/отмены скачивания.

Для прямого MP4 постоянная запись на диск не нужна. **Трафик обязательно идёт через VPS:** поток Boosty/CDN → VPS → ПК. При нестабильной сети разрыв браузерного скачивания может потребовать повторного начала; полноценное resume напрямую браузером требует безопасной поддержки `Range` и восстановимых ссылок.

Если источником является `m3u8`/DASH, браузер не обязательно может получить готовый `.mp4` простым проксированием: чаще требуется `ffmpeg` или временная сборка на диске с последующей выдачей и очисткой. Поэтому «на ПК без сохранения» означает **без постоянного хранения**, но не гарантирует полного отсутствия временных файлов.

**Не рекомендовать:** отдавать в браузер сырой `accessToken`, `refreshToken`, CDN signed URL или cookie Boosty. Прямой скачивание браузер→Boosty без VPS нельзя гарантировать из-за CORS, привязки CDN URL к IP, headers и протоколов контейнера. Для настоящей загрузки без прохода байтов через VPS понадобится дополнительный локальный клиент/агент (отдельный перспективный этап).

### B. «Сохранить на VPS»

Создать запись задания в SQLite → ограниченная очередь → запрос свежего URL → скачать во временный `.part` → при необходимости resume/проверка `206`, `Content-Range`, `ETag`/ключа медиа → `fsync` и атомарный `rename` → обновить БД → сделать файл доступным по защищённому внутреннему download endpoint. Задания переживают перезапуск. Ошибки обрабатываются по категориям: `401/403` требуют переподключения либо проверки прав; `429` — backoff; `5xx` — retry; истекшую ссылку CDN нужно заново разрешать, а не бесконечно запрашивать старую.

Поддержать квоты, предупреждения о нехватке места, отмену и ручное удаление. Политика: по умолчанию 1–2 одновременные задачи, регулируемый лимит; свободное место проверяется **до** скачивания, учитывая возможный размер временного контейнера.

### C. «Архивировать пост на сервере»

Отдельный `job_type=archive_post`: скачать/нормализовать содержимое поста, получить список ресурсов, загрузить все включённые типы ресурсов, опционально получить комментарии и вложения, сформировать безопасную HTML-страницу и машиночитаемый manifest, зафиксировать неизменяемый snapshot. «Открыть копию» не обращается к Boosty при каждом просмотре, а читает локальные данные и файлы. Доступ — только после авторизации в панели; публичные URL ресурсов не выдавать.

В отличие от отдельного видео, архив — единица из многих файлов. Загрузка считается `complete`, только если все **включённые** обязательные ресурсы загружены, HTML создан и целостность проверена. `partial` — если хотя бы один включённый ресурс отсутствует или для комментариев нельзя подтвердить полноту из-за API. `failed` — если ключевое содержимое поста не удалось получить. Отсутствие исключённых по выбору пользователя вложений НЕ переводит архив в `partial`.

Для автономного открытия: `index.html` + локальные CSS, изображения, видео/аудио (если выбраны), файлы (если выбраны) + JSON + comments JSON. Для закрытой веб-панели — тот же snapshot через внутренние защищённые маршруты. Внешние embeds (например, YouTube/VK) не являются автономной копией: при невозможности скачать их с правом доступа оставить ссылку и статус `external_dependency`, прямо показывая, что экспорт не полностью автономный. Подробнее — раздел 16.

## 5. Авторизация: два независимых контура

### Вход в сам веб-сервис

Пароль администратора, хеш Argon2id, ограничение попыток, защищённая серверная cookie сессии `HttpOnly; Secure; SameSite=Lax/Strict`, CSRF-проверка для мутирующих запросов, HTTPS. Опционально TOTP. Никакого входа на публичную панель без пароля. Восстановление доступа через консоль VPS, а не email-ссылку по умолчанию.

### Доступ к Boosty

1. **MVP:** вставка персонального `accessToken` через HTTPS в закрытой панели; тест запроса «проверить подключение». 2. Затем: `refreshToken + deviceId`, автоматически и строго сериализованно обновлять, сохранять сразу новую пару в зашифрованном vault. 3. Альтернатива — передавать экспортированный `auth` из своего браузера, корректно декодировать JSON и _clientId, без браузерных паролей и без хранения данных в `localStorage` панели. В версиях/браузерах Boosty данные могут быть в cookie или localStorage; фиксировать поддерживаемую схему по реальному тесту.

**Важный нюанс:** refresh-токен может ротироваться, а параллельное использование одной сессии браузером и сервером может её инвалидировать. Нужен `single-flight` refresh, атомарная запись пары и предупреждение об отдельных сессиях. Если refresh не работает — явный статус «Требуется повторный вход», без спама повторными запросами. Не пытаться воспроизводить форму логина Boosty с вводом пароля: нет подтверждённого официального OAuth для нашего сервиса, есть риск нарушения условий и обработки лишних секретов.

Токены хранить шифрованно AES-256-GCM (либо защищённым системным secret storage), ключ конфигурации отдельно, права каталогов `0700`/файлов `0600`; в stdout/journal и URL токенов не должно быть. Секреты никогда не отправляются на фронтенд обратно.

## 6. Нюансы Boosty и форматов

- Поддерживаемые публичные ссылки: `https://boosty.to/{blog}/posts/{uuid}`, `https://boosty.to/{blog}`, `https://boosty.to/{blog}/bundle/{id}`. Ссылки `/media/video/{post_uuid}/{video_uuid}` требуют отдельного распознавания и разрешения в пост + выбранный ролик. Тестировать URL с query/fragment/redirect и на соответствие доверенному домену.
- У одного поста может быть несколько роликов, в том числе разных поставщиков. Идентифицировать элементы по `(post_id, media_id)`; отображать каждый, не затирать одинаковые названия.
- Внешние YouTube, Vimeo, VK, OK и др. — не обязательно Boosty-файлы. В архиве по умолчанию отображать локальную карточку «Внешнее видео: не сохранено» и ссылку; не называть такой архив полностью автономным. Позже использовать специализированный обработчик с отдельной авторизацией и учётом правил внешней площадки.
- У native видео могут быть MP4-качества, HLS и DASH; выбираем **максимально доступное качество не выше заданного** с корректным fallback. Никогда не обещать 1080p, если API вернул только 720p.
- Ссылки CDN часто имеют подпись и срок жизни, возможна IP-привязка (`srcIp` встречается в `b00p`): нельзя сохранять их в БД для долгого использования, раздавать на другой компьютер и считать вечными.
- Бесплатное видео часто доступно без токена; аудио и вложения в отдельных сценариях могут требовать авторизации даже при бесплатном посте.
- Отсутствие права просмотра платного поста должно возвращать `not_entitled`, а не бесконечную перезагрузку.
- При массовом скачивании не хранить гигабайты в оперативной памяти, не делать безлимитную параллельность, учитывать rate limiting, лимит старых публикаций и пагинацию.
- Невозможно гарантировать работу во всех сетях/на всех зарубежных VPS; на этапе smoke-test нужно проверить именно VPS и типичный закрытый пост в законном доступе.
- DRM/зашифрованные потоки, которые нельзя законно обработать стандартными средствами воспроизведения пользователя, выводить как `unsupported_protection`; обход DRM не включать в план.
- «Все комментарии» ограничены тем, что реально выдаёт Boosty API: в `wpt/b00p` зафиксировано, что `offset` для comment endpoint игнорируется; ответы могут обрезаться по `reply_limit`, а список верхних веток — по `limit`. Нельзя гарантировать полный архив при большом количестве комментариев. Фиксировать `comment_count_reported`, `comment_count_archived`, `top_level_threads`, `replies_truncated`, `comments_complete=unknown/false/true` и показывать предупреждение.
- Удалённые комментарии иногда возвращаются как заглушки (`isDeleted`); сохранять структурное положение и статус удаления, не показывая отсутствующий текст как реально сохранённый.
- Посты могут обновляться после сохранения. Snapshot — версия на момент извлечения; обычный просмотр не зависит от дальнейших изменений Boosty, ручное «Обновить» создаёт новый snapshot, не перезаписывает предыдущую копию.

## 7. Безопасность веб-приложения

1. **SSRF:** разрешить на входе только URL с host `boosty.to` / `www.boosty.to`, строгая проверка схемы HTTPS и нормализация punycode; сервер получает медиа URL только из проверенного ответа Boosty API и применяет whitelist CDN-хостов + проверку редиректов/IP. Запретить запросы к localhost, RFC1918, link-local, metadata IP, file://, gopher:// и произвольным портам.
2. **Path traversal:** файл назначается только сервером под фиксированный root. Строки title и blog из API — данные, не путь; нормализовать `..`, слеши, Unicode, управляющие символы, зарезервированные имена, слишком длинные строки. Исключить symlink escape.
3. **Auth/ACL:** вся медиатека, задания, скачивание, SSE и удаление проверяют сессию владельца; нельзя открывать файлы по угадываемому ID. В single-admin это тоже обязательно.
4. **XSS:** описания постов и комментарии — недоверенный HTML. Нормализовать блоки, экранировать значения при построении HTML, whitelist тегов, CSP `default-src 'none'`, ограничивать ссылки и запрещать произвольный JavaScript, inline-handler и исполняемые вложения. Viewer и просмотр экспорта изолировать; `iframe` внешних сайтов не является частью автономного архива.
5. **Утечки секретов:** скрывать Authorization/Cookie/signed URL/параметры CDN в логах, трассировках и ответах об ошибке. Не хранить токен в истории запросов или в адресной строке. Резервные копии зашифровать.
6. **RCE:** никакого `sh -c` с URL/именем файла. `ffmpeg`/`yt-dlp` вызываются по argv, без параметров из пользовательского поля, с фиксированными лимитами, внешние выходные файлы только в sandbox.
7. **Resource exhaustion:** ограничения concurrent jobs, размера очереди, объёма диска, длительности задач, числа редиректов, скачивания больших файлов, лимиты прокси.
8. **Внешний доступ:** HTTP только для редиректа на HTTPS; для работы по IP рекомендуются защищённая частная сеть или корректно установленный сертификат; передачу Boosty-токенов по открытому HTTP запретить.

## 8. Модель данных SQLite (первый выпуск)

- `admins(id, username, password_hash, totp_secret_enc, created_at)`.
- `sessions(id_hash, admin_id, expires_at, last_seen)`.
- `boosty_accounts(id, label, access_enc, refresh_enc, device_id_enc, expires_at, status, updated_at)`.
- `posts(id, blog, title, fetched_at, access_state, raw_meta_sanitized)`.
- `media(id, post_id, external_id, provider, kind, selected_quality, mime, size_estimate, duration, title)`.
- `jobs(id, user_id, boosty_account_id, post_id, media_id, target, status, bytes_done, bytes_total, error_code, retry_at, created_at, updated_at)`.
- `files(id, job_id, storage_key, display_name, size, sha256, created_at)`.
- `archive_snapshots(id, post_id, source_updated_at, archived_at, options_json, version, status, completeness_json, manifest_path, html_path, total_bytes, root_path)` — неизменяемые версии поста.
- `archive_assets(id, snapshot_id, boosty_media_id, kind, original_name, local_relpath, mime, bytes, sha256, selected, status, failure_code)` — все ресурсы и причины исключения/ошибок.
- `archive_comments(snapshot_id, comment_id, parent_id, thread_id, author_name, created_at, updated_at, is_deleted, body_json, sort_order)` — дерево с полнотой и временем архивации.
- `archive_exports(id, snapshot_id, format, status, path, created_at, expires_at)` — временные ZIP-выгрузки с очисткой после выдачи.
- `settings(key, value)`; для критичных секретов отдельный vault.

Статусы: `validating → queued → resolving → downloading → processing → completed`, а также `waiting_auth`, `failed`, `cancelled`. Переходы атомарны; при старте восстанавливаются `downloading`/`processing`. Для HTTP stream-to-browser можно использовать эфемерное задание без постоянного файла.

## 9. API (предлагаемый контракт)

```http
POST   /api/v1/session/login
POST   /api/v1/session/logout
GET    /api/v1/session/me
POST   /api/v1/boosty/accounts            # импорт токенов
POST   /api/v1/boosty/accounts/{id}/test
DELETE /api/v1/boosty/accounts/{id}
POST   /api/v1/resolve                   # URL → пост + media choices
POST   /api/v1/jobs                      # target: server
GET    /api/v1/jobs
GET    /api/v1/jobs/{id}
GET    /api/v1/jobs/{id}/events           # SSE
POST   /api/v1/jobs/{id}/cancel
GET    /api/v1/media/{id}/stream          # target: pc, stream-to-browser
GET    /api/v1/files/{id}/download        # download from VPS
DELETE /api/v1/files/{id}
POST   /api/v1/archive/posts             # URL + include_comments/include_attachments/include_media
GET    /api/v1/archive/posts             # список сохранённых снимков
GET    /api/v1/archive/posts/{id}        # manifest, полнота, опции, метаданные
GET    /library/posts/{id}               # защищённая копия для просмотра
GET    /api/v1/archive/posts/{id}/assets/{asset_id} # защищённый доступ к ресурсам
POST   /api/v1/archive/posts/{id}/export # построить переносимый ZIP
GET    /api/v1/archive/exports/{id}/download # одноразовая авторизованная выдача
POST   /api/v1/archive/posts/{id}/refresh  # новый snapshot, не перезаписывать
GET    /api/v1/system/storage
GET    /healthz                          # internal/liveness
```

`POST /resolve` не скачивает видео; ответ включает `provider`, `video_id`, `qualities`, `access_state`, ожидаемый размер (если API даёт), пост, автора, миниатюру. Контракт ошибок: `INVALID_URL`, `AUTH_REQUIRED`, `NOT_ENTITLED`, `TOKEN_EXPIRED`, `RATE_LIMITED`, `MEDIA_UNSUPPORTED`, `STORAGE_FULL`, `REMOTE_ERROR`, `CANCELLED`, `ARCHIVE_PARTIAL`, `COMMENTS_TRUNCATED`, `ASSET_MISSING`, `EXTERNAL_DEPENDENCY`. Для длинных задач прогресс по SSE; проверять ACL, поддержку reconnect и backoff клиента. Поток на ПК может запускаться через POST + одноразовый внутренний ticket, чтобы не помещать секреты в адресную строку; файл выдаётся на короткоживущем внутреннем URL после проверки сессии.

## 10. Установка и обслуживание без Docker

Путь установки (рекомендуемый):

```
/opt/boosty-web/boosty-web          # один бинарник + встроенные статические файлы
/etc/boosty-web/config.toml        # конфигурация, без открытых токенов
/etc/boosty-web/master.key         # 0600, вне git и backup без шифрования
/var/lib/boosty-web/state.db       # SQLite WAL
/var/lib/boosty-web/media/         # готовые файлы
/var/lib/boosty-web/archives/      # снимки постов / HTML / локальные ресурсы
/var/lib/boosty-web/exports/       # временные ZIP для скачивания
/var/lib/boosty-web/tmp/           # .part и временные HLS/DASH
/var/log/...                       # предпочтительно journalctl
```

`install.sh` с режимами `--domain example.com` и `--ip ...` (режим IP безопасно открывать через TLS/частную сеть), выбор порта, пользователя, директории медиатеки, создание systemd unit и reverse-proxy конфигурации; `uninstall.sh`, `update.sh`, `backup.sh`, проверка отката. Исключить локальный desktop-run и Docker как обязательные компоненты. Из установки не делать интерактивного небезопасного скачивания исполняемого файла из неподтверждённого источника: релизы, SHA256 и проверка архитектуры `amd64`/`arm64`.

Для первого запуска ориентир — 1 vCPU/1 GB RAM при ограниченном параллелизме **без транскодирования**; это проектная стартовая гипотеза, подтверждается нагрузочными тестами. Для DASH/HLS и `ffmpeg`, нескольких пользователей и параллельных заданий нужны дополнительные CPU/диск. Скорость ограничивается сетью Boosty/CDN, VPS и маршрутом до пользователя. Одно скачивание на ПК в размере X передаёт приблизительно X входящих и X исходящих байт VPS, не считая служебных запросов.

Для медиатеки выделить отдельный диск/volume. Не рассчитывать на маленький системный раздел: Boosty официально указывал возможность загружать видеоролики объёмом до 20 ГБ, конкретные размеры зависят от контента и качества.

## 13. Приёмочные проверки — обязательно до публикации

- [ ] Открытый одиночный MP4 без Boosty-токена → успешно в ПК-режиме.
- [ ] Оплаченный пост при действующем доступе → успешно в двух режимах.
- [ ] Платный пост без подписки → `NOT_ENTITLED`, нулевое скачивание.
- [ ] Истёкший access token и валидный refresh → один refresh, задача восстановлена.
- [ ] Истёкший refresh → статус reconnect, секреты не попадают в журнал.
- [ ] Два ролика в одном посте → оба видны, выбираются независимо.
- [ ] Ссылка на `/media/video/...` → выбирается конкретный media ID.
- [ ] HLS / DASH → корректная сборка и чистка временных файлов.
- [ ] Обрыв загрузки с VPS / рестарт systemd → безопасный resume.
- [ ] Неправильный `Content-Range` / изменившийся CDN-файл → начать заново, не склеить разные объекты.
- [ ] Закрытие вкладки при stream-to-PC → отмена upstream и отсутствие накопления на диске.
- [ ] Попытка скачать чужой файл по ID → 403/404 без утечки.
- [ ] URL к localhost/private IP, redirects, DNS rebinding → блокируется.
- [ ] HTML-содержимое со скриптами, поддельные имена файлов → безопасный рендер/санитизация.
- [ ] Заполненный диск / деградация сети / 429 → понятная ошибка, целый SQLite, частичный файл можно возобновить.
- [ ] Установка Debian/Ubuntu amd64/arm64, домен и закрытый IP-режим → проверены.
- [ ] Публичное открытие панели не раскрывает cookie, URL файлов и списки задач.
- [ ] Архив поста без комментариев и вложений → полноценный текст/картинки/плеер, исключённые элементы явно отмечены, `complete` при сохранении всех выбранных ресурсов.
- [ ] Архив с комментариями → сохранена вложенность, авторы/даты, удалённые заглушки не отображаются как полноценные сообщения.
- [ ] Превышение предела комментариев/ответов API → `partial`, показано количество найденных, предупреждение о неполноте.
- [ ] Архив с вложениями → файлы открываются только с авторизацией, сохраняют MIME/размер/checksum и допустимые имена.
- [ ] Скопированный архив в ZIP → `index.html` открывается без сервера и без Boosty, без абсолютных ссылок на локальные ресурсы.
- [ ] Встроенное внешнее видео не скачано → карточка с оригинальной ссылкой, `external_dependency`; система не заявляет полностью автономный экспорт.
- [ ] Удалённый или изменённый оригинал → уже сохранённая версия доступна без внешних API запросов.
- [ ] Повторная архивация обновлённого поста → создаёт snapshot v2, не уничтожая v1.
- [ ] Вредоносный HTML в посте/комментариях → не исполняется в viewer и ZIP; ошибки доступа к архивам дают 403/404.

## 14. Решения, которые стоит зафиксировать до кодирования

1. Сервер прежде всего **single-admin**, никаких общих публичных загрузок.
2. Две равноправные главные функции — **видео** и **полная копия одного поста**. Блог/бандлы пакетно — позже; для архива обязательны текст и изображения, видео/аудио по умолчанию включены, комментарии и прикреплённые файлы опциональны.
3. Основной стек — **Go + React + SQLite WAL + systemd**; установка без Docker по IP или домену, но секреты только по защищённому каналу.
4. Три режима: `stream-to-pc`, `save-to-server`, `archive-post`. Последний создаёт версионированный, доступный для чтения snapshot со статусом полноты.
5. Медиа из других сервисов/DRM — не обещать автоматически, отдельный optional executor.
6. Код из сторонних проектов использовать только с соблюдением лицензий и отдельным security review; не копировать целый desktop Tauri.

## 16. Спецификация: автономная копия полного поста (новое требование, v1.1)

### Результат

Каждая архивная копия — самостоятельная **версия поста** с данными, доступными на момент скачивания. В серверной панели кнопка «Открыть копию» ведёт на `/library/posts/{snapshot_id}`. Текст и оформление, автор, дата/время, обложка, теги, изображения, native видео/аудио (при включении) и ссылки отображаются как страница поста. Ни HTML, ни медиаконтент этой страницы не требуют нового запроса к Boosty. Сервер выдаёт сохранённые файлы через свою авторизованную раздачу, с HTTP Range для просмотра больших видео в браузере. По желанию можно скачать переносимый ZIP и открыть `index.html` без VPS.

**UI-флажки:** `Сохранить комментарии и ответы` (по умолчанию выключено, во избежание неожиданной массовой загрузки), `Сохранить прикреплённые файлы` (по умолчанию выключено), `Сохранить видео и аудио` (по умолчанию включено), `Качество` (лучшее доступное по умолчанию). Текст, метаданные и изображения включены всегда. Если пользователь выбрал полный архив, но отключил отдельные флажки, эти части считаются намеренно исключёнными; manifest точно описывает состав. Повторное включение опции при новом скачивании создаёт новую версию или выполняет адресное дополнение ресурса с фиксацией новой версии.

### Модель полного снимка

- Источник: `boosty_url`, `blog`, `post_id`, `source_created_at`, `source_updated_at`, `archived_at`, `account_id` (в зашифрованной конфигурации, не внутри ZIP), `snapshot_version`.
- Контент: нормализованное дерево блоков (`text`, `heading`, `paragraph`, `list`, `link`, `image`, `video`, `audio`, `file`, `embed`, `unknown`) + оригинальные JSON-поля, очищенные от токенов и подписанных URL, чтобы можно было улучшать рендер без повторного запроса.
- Комментарии: ID, ID родительского комментария, ID ветки, вложенность, автор/публичный аватар (при доступности), текст/медиа, порядок, даты создания/редактирования, статус удаления; дерево строится из связей, не из простого отступа HTML.
- Вложения: список всех исходных названий, MIME, размеров, локальных относительных путей, контрольных сумм, признаков `downloaded/omitted/failed`.
- Качество и полнота: `requested_options`, `available_media_count`, `downloaded_media_count`, `expected_comment_count` (если известен), `archived_comment_count`, `replies_truncated`, `unresolved_resources[]`, `completeness_state`.

### Файловая структура

```text
/var/lib/boosty-web/archives/
  {blog-slug}/
    {post-id}/
      snapshot-0001/
        manifest.json             # форматы, опции, полнота, checksum
        post.json                 # нормализованный контент
        comments.json             # только если включён сбор комментариев
        index.html                # автономная копия, относительные пути
        assets/
          style.css               # локальный CSS без внешних зависимостей
          image-001.jpg
          video-001.mp4
          audio-001.m4a
          comment-image-001.jpg
        attachments/
          attachment-001.pdf
        checksums.sha256
      snapshot-0002/             # обновлённая версия, без перезаписи старой
```

На диске имена должны быть техническими стабильными ID, не сырыми именами пользовательских файлов; привлекательные заголовки отображать в интерфейсе. Возможна дедупликация по sha256 во внутреннем blob-store с безопасным reference counting, но не в MVP. ZIP создаётся из готового snapshot только после проверки локальных зависимостей, не включает секреты и никогда не читает файлы за пределами archive root.

### Пайплайн архивации

1. Проверить URL и право доступа → получить пост целиком и его начальные метаданные; записать `job` и `archive_snapshot(status=building)`.
2. Сериализовать все известные блоки, порядок, авторство, теги и описания в безопасный `post.json`, включая неизвестные типы данных для диагностики, но без секретных URL.
3. Скачать изображения, обложки, аватары при необходимости, видео/аудио выбранного качества; вложения — только при флажке. Для каждого ресурса сохранять `status`, размер и sha256.
4. Если включены комментарии, запросить доступные верхние ветки с максимальной безопасной нагрузкой, подгрузить вложенные ответы, где это поддерживается; отслеживать `replyCount`, `isDeleted`, лимиты и фактические счётчики. При неизвестной или ограниченной полноте не ставить `complete` для комментариев.
5. Сформировать безопасный HTML с локальными `src`/`href`, навигацией по комментариям, плеерами с `controls`, стилями и разметкой. При отсутствии ресурсов показывать явные placeholder и причину.
6. Сравнить manifest и файлы, проверить контрольные суммы, записать `checksums.sha256`, атомарно перевести снимок в `complete/partial/failed`, отправить событие SSE.
7. Защищённый viewer раздаёт HTML и файлы с обязательной проверкой сессии; экспорт ZIP пересобирает разрешённую структуру с **относительными** путями, чтобы содержимое было открываемо за пределами сервера.

### Что значит «полная копия»

Нужно различать `archived_exactly_as_selected` — скачано всё, что пользователь **включил**, и `source_completeness_confirmed` — API не ограничил данные. Эти признаки независимы. Пример: пользователь выключил комментарии и вложения; архив успешно сохранён, но интерфейс показывает «Комментарии и вложения не включены», а не «Сохранено всё». Другой пример: пользователь включил комментарии, сервер получил 101 ветку при `expected_count=150`; статус `partial` с пояснением «вероятно ограничение API», а не ложное обещание полного сохранения.

У `wpt/b00p` в `pkg/boosty/client.go` и `pkg/boosty/urls.go` задокументированы ограничения: comment `offset` может игнорироваться; для вложенных ответов нужен `reply_limit` (референс использует `100`), а слишком длинные ветки могут быть обрезаны. `pkg/syncer/save.go` отдельно помечает `CommentsCapped` и сравнивает реальные количества. Это **наблюдение стороннего клиента**, а не официальная гарантия API: в нашем проекте адаптер и тесты должны проверять текущее поведение.

`ath31st` в `core/src/menu_handler.rs`, `core/src/comment_handler.rs` и `core/src/post_page.rs` уже умеет получать комментарии через `get_all_comments`, строить вложенные отображения и сохранять `index.html`; это хороший референс. Сохранение **всех** комментариев для произвольного поста должно быть обозначено как best effort с индикацией неполноты до реального подтверждения подходящей пагинации.

### Тонкости архивного viewer

- Viewer и JSON/ZIP endpoints доступны только авторизованному владельцу. Никакой публичной индексации, поиск/список архивов без логина закрыты.
- Внутри ZIP нельзя ссылаться на ресурсы с VPS и Boosty, кроме отдельно обозначенных оригинальных внешних ссылок. Внешний iframe не вставлять в офлайн-страницу: он всё равно требует интернет и создаёт риски.
- Комментарии и названия вложений — недоверенные пользовательские данные; встроенный HTML должен быть безопасным даже при открытии локально. Не разрешать внешние скрипты/обработчики событий и опасные `javascript:` ссылки. Для online viewer — строгий CSP, `X-Content-Type-Options: nosniff`, правильный тип файлов.
- «Воспроизвести» использует локальный MP4 и Range, без нового обращения к Boosty. Если исходный формат HLS/DASH и конвертация не удалась, архив отмечается частичным.
- ZIP-бэкапы могут содержать личные данные авторов комментариев — выдавать только собственнику через HTTPS; пользователь обязан учитывать права на распространение контента.
- В интерфейсе показывать `Версия`, `Создано`, `Обновлено у автора`, `Сохранено: n из m`, `Пропущено по выбору`, `Не удалось получить`, `Комментарии: n / ожидается m`, `Полнота неизвестна`.

### Приёмка функции

1. Архив закрытого поста с действующим доступом открывается на VPS после разлогина Boosty, без запросов к Boosty.
2. Копия переносится ZIP на другой компьютер; изображения и видео работают с относительными путями без сети.
3. При выключенных комментариях/вложениях архив не содержит этих файлов, а интерфейс явно маркирует исключения.
4. При включённых комментариях с ответами сохранены связи parent-child, даты и авторы; лимит API детектируется как `partial`.
5. Изменение или удаление оригинала не меняет старый архив, обновление делает snapshot v2.
6. При остановке задания наполовину исходный snapshot остаётся в состоянии `building/partial`; не появляется ложная завершённая копия.
7. HTML со встроенными скриптами, именами `../`, URL с внутренними IP и враждебными вложениями не нарушает изоляцию панели.
8. Экспорт ZIP не содержит accessToken, refreshToken, cookie, signed CDN query или путей вне папки архива.


## 17. Дополнительный сравнительный аудит lowfc и требование «открыть полную копию» (v1.2)

Проверено по реальным файлам ветки `master` проекта [`lowfc/boosty_downloader`](https://github.com/lowfc/boosty_downloader) на 10.11.2026. Осмотр кода не заменяет функциональное тестирование Boosty API на живом аккаунте.

### Чем полезен lowfc и чего в нём недостаточно

| Проверенный узел | Фактическое поведение в коде | Решение для веб-архива |
|---|---|---|
| `src/pages/download_post.py` | Принимает URL конкретного поста, добавляет задачу через `DownloadManager` | Повторить удобство единого поля ссылки и предпросмотра |
| `src/core/boosty/client.py` | `get_post_info()` читает `/v1/blog/{author}/post/{post_id}`, типизирует текст, image, `ok_video`, audio, file, link, list; `get_posts_list()` устанавливает `comments_limit=0`, `reply_limit=0` | Добавить независимый comments fetcher и работу с вложенными ветками |
| `src/core/task.py` | Формирует текст `content.txt` или `content.md`, сохраняет файлы в папку поста; настройки `need_download_*` отключают категории | Добавить snapshot `post.json`, локальные CSS/HTML, индексацию и независимый viewer |
| `src/core/downloads_manager.py` | Очередь хранится в памяти приложения, пул ограничен семафором | Хранить задания и права доступа в SQLite, восстанавливать после рестарта |
| `src/core/authorization_provider.py` | Ввод/запоминание токена в Flet SharedPreferences | Серверный vault и безопасное обновление/отзыв токена |
| `LICENSE.md` | Явно заявлены CC BY-NC 4.0 и дополнительные ограничения, включая личное некоммерческое использование и ограничения на копирование чужого содержимого | Брать UX-идеи, но **не копировать код** без отдельной правовой оценки; учесть права авторов Boosty |

**Вывод:** низкоуровневая выгрузка данных/медиа у lowfc уже существует, но полноценной просмотрной автономной копии поста с комментариями и ветками ответов в проверенном процессе `Task._run()` нет. Для требуемого веб-приложения нужна собственная функциональность архивации, а не просто перенос Flet на сервер.

### Требуемый UX архива по ссылке

Три режима должны быть равноправны: **«Скачать видео на ПК»**, **«Сохранить видео на VPS»**, **«Архивировать пост»**. В третьем режиме доступны отдельные опции:

- Текст, заголовок, дата, автор, теги, изображения и оформление — всегда сохранять.
- Видео/аудио и качество — переключаемое, по умолчанию включать.
- **«Сохранить комментарии и ответы»** — независимо переключаемое, по умолчанию выключено; если включено, загружать максимально полное доступное дерево (ID, parent_id, автор, время, текст, медиа, вложения и статусы удаления).
- **«Сохранить прикреплённые файлы»** — независимо переключаемое, по умолчанию выключено; применять как к посту, так и к комментариям, если их данные доступны. В описании показывать количество и размер до запуска, когда известны.
- Сохранять комментарии **в текстовом виде** даже при выключенных вложениях, но не подменять удалённые/недоступные содержимое и не скрывать факт отсутствующих ресурсов.

Сразу после окончания появляется запись в разделе **«Архивы»** с действиями **«Открыть копию»**, **«Скачать ZIP»**, **«Повторить неполные элементы»**, **«Создать новую версию»**, **«Удалить»**. Копия открывается по защищённому маршруту `/library/posts/{snapshot_id}`. На странице должны работать локальные изображения, оригинально форматированный текст (через безопасный рендер), ссылки на файлы, браузерные video/audio controls и дерево комментариев. Никакого обращения к Boosty для уже сохранённого контента. После выключения Boosty-авторизации архив по-прежнему доступен администратору панели.

### Подтверждённая проблема с количеством комментариев

Исходники [`wpt/b00p/pkg/boosty/client.go`](https://github.com/wpt/b00p/blob/master/pkg/boosty/client.go) и [`pkg/boosty/urls.go`](https://github.com/wpt/b00p/blob/master/pkg/boosty/urls.go) документируют наблюдаемое поведение: `offset` для `comment` API может не поддерживать получение следующих страниц; сервер встраивает ответы только при `reply_limit`, а ограниченный размер может обрезать ветку. В [`pkg/syncer/save.go`](https://github.com/wpt/b00p/blob/master/pkg/syncer/save.go) предусмотрено определение усечения. Это ограничение стороннего клиента, не официальная спецификация Boosty; при тестах адаптер обязан сверить `expected_count`, реально сохранённое количество, вложенные `replyCount`, заглушки удалённых сообщений и возможные способы загрузки дополнительных страниц.

Если сервер не смог получить 100% — писать **«Архив частичный»** и перечислять недоступные элементы, а не заявлять, что сохранены «все комментарии». При последующем обновлении попытаться добавить пропущенные ID, сохранить стабильные IDs, не дублировать совпавшие комментарии, не портить уже готовый snapshot.

### Требование к «полной копии» в двух смыслах

- **Серверный архив:** просмотр через закрытую медиатеку, сохранённые ресурсы раздаются с VPS, для видео поддерживается HTTP Range. Шаблон не требует исходных CDN-ссылок.
- **Переносимая автономная копия:** ZIP с `index.html`, `manifest.json`, `post.json`, `comments.json` (по выбору), локальными изображениями/видео/аудио/вложениями и CSS, абсолютных ссылок на VPS и Boosty как обязательных ресурсов нет. Внешние iframe и сторонние видео не считать локально сохранёнными: показывать ограничение явно.

Безопасность: каждый архив приватный по умолчанию; выдача файлов и ZIP по сессии администратора, запрет XSS в теле поста/комментариях, path traversal в названиях и SSRF в URL вложений. Упаковывать только реальные сохранённые ресурсы из whitelist каталога, не включать токены и подписанные URL. Копирование чужих платных материалов не должно вести к их публичному распространению.

### Дополнительные критерии приёмки

- [ ] Пост с тремя видео, изображениями и вложениями открывается как единая локальная HTML-страница на VPS; все включённые ресурсы локальные.
- [ ] Комментарии с ответами сохраняют дерево, авторов, даты и вложения в рамках выбранных параметров.
- [ ] Отключение комментариев и вложений не удаляет обязательные текст/изображения и не приводит к пустым/сломанным ссылкам.
- [ ] Если Boosty API обрезает верхнеуровневые ветки или ответы, отображается `partial` с фактическими и ожидаемыми количествами, где они известны.
- [ ] Архив остаётся открываемым после завершения Boosty-сессии и после удаления/изменения оригинального поста (при условии, что ранее контент был сохранён).
- [ ] ZIP открывается на другом ПК без VPS; тест без интернет-соединения подтверждает воспроизведение всех действительно сохранённых ресурсов.
- [ ] Повторное обновление создаёт следующую версию или дополняет недостающие ресурсы атомарно, не разрушая предыдущую завершённую копию.
