# SQLite: текущий статус и безопасные операции

**Основное хранилище сервера — JSON.** `jobs.json` и `imports.json` управляют заданиями и импортом, `accounts.json` — пользователями. SQLite **не** используется для принятия решений о правах или выдаче файлов.

SQLite v1 используется для офлайн-экспорта, проверки, экспериментального Shadow и переиндексации истории. **Автоматическое production-переключение и откат SQLite ↔ JSON пока не реализованы.**

## Главное правило

Каждый архив принадлежит своему пользователю. Общий оригинальный пост и одинаковый SHA-256 медиа не дают другому пользователю права читать архив. Доступ к Boosty всегда определяется правами конкретного аккаунта. SQLite хранит метаданные; большие файлы остаются на диске.

## Где что находится

- `/var/lib/boosty-downloader/jobs.json`, `imports.json` — рабочие JSON.
- `library/<owner>/<author>/<post>/` — текущая версия архива.
- `revisions/<owner>/<author>/<post>/<revision>/` — исторические версии.
- `blobs/sha256/<2>/<digest>` — дедуплицированные файлы.
- `metadata.db` — необязательная SQLite схемы v1.

Схема: [schema_v1.sql](../deploy/sqlite/schema_v1.sql).

При Native утилита `boosty-dbcheck` устанавливается вместе с сервером. Для Docker скачайте одноимённый бинарник своей архитектуры из GitHub Releases и проверьте его SHA-256, либо соберите `go build ./cmd/boosty-dbcheck` из исходников и запускайте на хосте. Docker-образ не получает root-доступ к хосту.


**Блокировка каталога данных:** сервер удерживает системную эксклюзивную блокировку каталога до остановки. `boosty-dbcheck` (проверка, резервная копия, переиндексация, аудит), Python-экспорт `tools/sqlite_migrate.py` и сброс пароля администратора отказываются работать при занятом каталоге. Второй сервер с тем же `data-dir` не запускается. Блокировка не заменяет остановку всех сторонних процессов, которые могут напрямую редактировать файлы, и полный snapshot VPS. Удалять служебные файлы для обхода блокировки не требуется: она привязана к открытым дескрипторам каталога.

## Экспериментальное онлайн-чтение каталога из SQLite (этап 12.3.3)

Начиная с этого этапа сервер поддерживает **добровольный SQL-индекс для чтения** трёх пользовательских API: `GET /api/catalog`, `GET /api/jobs` и `GET /api/shared`. По умолчанию механизм **выключен**: все операции продолжают работать на JSON.

Чтобы испытать режим, сначала **остановите сервер**, сохраните независимую копию данных и убедитесь, что существует согласованный `metadata.db` схемы v1. Затем установите в конфигурации окружения сервера оба параметра:

```ini
BD_SQLITE_SHADOW=1
BD_SQLITE_CATALOG_READS=1
```

Включение `BD_SQLITE_CATALOG_READS=1` без `BD_SQLITE_SHADOW=1` блокирует запуск. При старте Shadow сначала сверяет SQL с исходными JSON. Каталог выполняет параметризованный запрос к SQL только при успешной синхронизации, после чего **сверяет весь набор найденных идентификаторов с текущим JSON и применяет реальные ACL из JSON**. SQL никогда не предоставляет права на чужой архив: поддельная SQL-выдача, неверный владелец, отсутствие записей, истёкший таймаут (500 мс) или отставание проекции приводят к автоматическому чтению из JSON без потери результатов.

Через `GET /api/admin/sqlite-shadow` администратор видит `catalogReadsEnabled` и общее состояние Shadow. Статус `healthy` означает успешную синхронизацию проекции, но не превращает SQL в источник прав. **Это переходный режим совместимости, а не ускоренная SQL-primary база:** полный JSON-снимок и проверка ACL пока сохраняются ради безопасности. Для возврата достаточно выключить `BD_SQLITE_CATALOG_READS` и перезапустить сервер, не удаляя данные.

**Не включено:** транзакционные SQL-записи как основной источник, переключение прав и очередей на SQLite, автоматический cutover/rollback и восстановление целого VPS. `jobs.json`, `imports.json` и текущие файловые ACL продолжают оставаться авторитетными.

## Транзакционная фиксация метаданных SQLite из работающего сервера

При `BD_SQLITE_SHADOW=1` администратор может открыть **Настройки → SQLite: синхронизация метаданных** и нажать **«Зафиксировать метаданные в SQLite»**. Аналогичная авторизованная операция доступна через `POST /api/admin/sqlite-shadow/commit`. Она **не требует** включения `BD_SQLITE_CATALOG_READS` и не запускается автоматически по обычному запросу чтения.

Операция выполняет следующие проверки в одном контролируемом процессе:

1. Не ожидая длительного сканирования медиа, захватывает единственную блокировку записи SQL-проекции. Если занят фоновый SQL-писатель, возвращает HTTP 409.
2. Читает авторитетные **сохранённые на диске** `jobs.json` и `imports.json` с учётом журнала восстановления JSON.
3. В одной SQL-транзакции обновляет записи публикаций, состояния задач, импорты и разрешения, одновременно сверяя нормализованные столбцы SQL с JSON. При повреждённых/поддельных разрешениях транзакция не подтверждается.
4. После SQL-коммита перечитывает SQL и сравнивает полный набор записей с исходным JSON-снимком.
5. Проверяет номер поколения JSON, прежде чем подтвердить успешную синхронизацию. Если JSON изменился во время процедуры, возвращает HTTP 409, оставляя новую версию в очереди фоновой синхронизации.

Успешный HTTP 200 означает, что **метаданные** SQLite соответствовали выбранному согласованному поколению JSON. HTTP 503 сообщает о сбое SQL или несоответствии, при этом **JSON не переписывается и права пользователей не меняются**. История медиа, CAS и файлы архивов этой операцией не изменяются; для них действует отдельная проверка `--cutover-preflight`.

Это **не перевод на SQL-primary** и не атомарная двухфазная транзакция между двумя разными хранилищами: запись JSON была завершена раньше и остаётся основным источником. Для SQL-primary нужны отдельные журнал переключения, резервная копия, атомарный cutover/rollback и аварийные E2E.

## Аварийно-безопасная репетиция перехода на SQLite (этап 12.3.4)

Перед переключением на SQL-primary доступна отдельная **офлайн-репетиция** с долговечным журналом `.sqlite-cutover-intent.json`. Она проверяет саму процедуру подготовки и восстановления после неожиданного завершения программы, но **не включает SQL-primary и не изменяет JSON/SQLite/медиа**.

Сначала остановите сервер и все сторонние процессы записи. Создайте резервную копию метаданных **вне каталога данных** и выполните строгий аудит (должны совпадать JSON, нормализованные SQL-данные, разрешения, архивные файлы и SHA-256 медиа). Затем:

```bash
# Сервис остановлен. BACKUP должен быть уже проверенным снимком метаданных.
boosty-dbcheck --data-dir /var/lib/boosty-downloader \\
  --prepare-sqlite-cutover \\
  --recovery-dir /path/outside/data/verified-metadata-backup

# При необходимости отменить подготовленный журнал без запуска сервера:
boosty-dbcheck --data-dir /var/lib/boosty-downloader \\
  --recover-sqlite-cutover
```

Операция подготовки резервирует блокировку каталога, подтверждает **неизменность приватного снимка**, фиксирует SHA-256 его манифеста и атомарно записывает журнал с `fsync`. Попытка при запущенном сервере, при наличии другого журнала, неполном SQLite WAL, повреждённом SQL или невалидном резервном снимке отклоняется.

При **следующем запуске сервера** подготовленный журнал распознаётся до загрузки учётных записей и запуска фоновых задач. Если резервная копия всё ещё идентична исходной, а SQL/JSON/ACL/медиа совпадают, подготовка автоматически отменяется с синхронизированным удалением журнала. Если снимок подменён, файл журнала опасен, есть несоответствие, либо не удалось синхронизировать отмену, сервер **отказывает в старте**; пользовательские данные при этом не переписываются. Ручная отмена выполняет те же строгие проверки.

Добавлены тесты с реальным `SIGKILL` непосредственно **до** и **после** записи долговечного журнала, с моделированием `ENOSPC` на обеих стадиях, с подменой манифеста, изменением JSON, симлинком вместо журнала и с занятым каталогом.

**Ограничение:** это подготовка протокола аварийного переключения, а **не активный SQL-primary**. Команда не должна использоваться как восстановление изменённых после снимка данных. Если во время аварии изменения всё-таки произошли, автоматическое переписывание более свежего JSON запрещено; требуется отдельная ручная проверка и восстановление из полной резервной копии. Для настоящего переключения ещё необходимы авторитетные SQL-записи, активный флаг backend, полноформатный rollback и аварийные E2E самого момента смены источника данных.

## Безопасная офлайн-проверка

**Перед началом остановите сервис и все фоновые процессы записи, сделайте полную копию `/etc/boosty-downloader/` и `/var/lib/boosty-downloader/`.** Не выполняйте операции на изменяющихся архивных файлах. Если используется Docker, остановите контейнер через `sudo bdy stop`.

Из корня репозитория:

```bash
sudo bdy stop

# Новый путь metadata.db должен отсутствовать.
sudo python3 tools/sqlite_migrate.py \
  --data-dir /var/lib/boosty-downloader \
  --output /var/lib/boosty-downloader/metadata.db

# В Native используется boosty-dbcheck, установленный вместе с сервером.
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader

sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader --audit-media
```

`--audit-media` проверяет внешние ключи, индексы версий, манифесты, пути владельцев, CAS и SHA-256 реальных файлов. Не исправляет и не удаляет данные. Если есть **непустой WAL**, аудит откажется работать: нужно корректно закрыть SQLite и выполнить checkpoint, а не удалять WAL вручную.

## Проверенная копия метаданных

```bash
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader \
  --backup-dir /root/boosty-metadata-backup-001

sudo boosty-dbcheck \
  --verify-backup-dir /root/boosty-metadata-backup-001
```

Каталог `--backup-dir` должен быть **новым** и находиться вне основного каталога данных. Проверяются SHA-256, JSON, схема SQL, владельцы и ACL. Копия содержит **только метаданные** — это не резервная копия медиа, токенов, TLS-ключей или всего VPS.

## Полная офлайн-копия каталога данных (архивы + медиа + метаданные)

В отличие от `--backup-dir` (только метаданные), `--full-snapshot-dir` создаёт **новую частную копию всего каталога данных**, включая `library/`, `revisions/`, `blobs/`, учётные записи и расположенные там секреты. Сервер и другие процессы записи должны быть остановлены.

```bash
sudo bdy stop
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader \
  --full-snapshot-dir /root/boosty-data-snapshot-001

# Независимая повторная проверка без доступа к исходному серверу:
sudo boosty-dbcheck --verify-full-snapshot-dir /root/boosty-data-snapshot-001
```

Путь назначения должен отсутствовать и физически находиться **вне** каталога данных, с достаточным свободным пространством. Снимок включает каталог `data/` с файлами и `snapshot-manifest.json` с SHA-256, размером и исходными режимами прав каждого файла. Каталоги копии имеют режим 0700, файлы — 0600. Файлы копируются потоково; исходные симлинки, устройства, FIFO, незавершённый журнал JSON или непустой WAL запрещены. После копирования проверяются имена источников, каждая копия и её SHA-256; неполный новый снимок при ошибке удаляется. Команда может занимать продолжительное время и требовать дополнительное пространство для повторяющихся файлов/hardlink.

**Границы:** это снимок **каталога данных приложения**, а не целого VPS. Он не включает `/etc/boosty-downloader/`, внешние TLS-ключи, systemd-конфигурацию, бинарники, окружение и файлы на других путях. Для восстановления всей установки отдельно сохраните эти компоненты и полный snapshot VPS. Программное автоматическое восстановление каталога из снимка пока не добавлено: не копируйте его поверх запущенного приложения. Контрольные суммы обнаруживают повреждения, но не защищают от атакующего, который имеет доступ к изменению самих файлов и манифеста. Рекомендуется хранить вторую копию вне VPS.

## Восстановление полного снимка в новый каталог (без перезаписи сервера)

Восстановление поддерживает только **отдельный новый путь**. Команда никогда не заменяет существующую установку и не меняет исходный снимок.

```bash
# Создать отдельный восстановленный каталог. Путь назначения не существует.
sudo boosty-dbcheck \
  --restore-full-snapshot-dir /root/boosty-data-snapshot-001 \
  --restore-to /root/boosty-restored-data-001

# Проверить исходный снимок независимо от живого сервера:
sudo boosty-dbcheck \
  --verify-full-snapshot-dir /root/boosty-data-snapshot-001
```

Восстановление заново проверяет каждый SHA-256 снимка, фиксирует исходный манифест, копирует файлы через Linux `openat(O_NOFOLLOW)` для каждого компонента пути, повторно проверяет восстановленные файлы и повторно проверяет снимок. Временный каталог создаётся рядом с местом назначения и публикуется атомарно через `renameat2(RENAME_NOREPLACE)`. Если кто-то создаст каталог назначения параллельно, команда **откажет без перезаписи**. При штатной ошибке временные данные удаляются, после аварийного `SIGKILL` приватный временный каталог может остаться с префиксом `.boosty-full-restore-`; рабочий каталог назначения остаётся недоступен до успешной публикации.

Восстановленная копия защищена правами 0700 для каталогов и 0600 для файлов. Исходные режимы сохранены в манифесте, но автоматически не применяются для предотвращения раскрытия личных данных. **Владельцы файлов, права запуска службы, внешние TLS-ключи, конфигурация `/etc` и systemd не восстанавливаются.** Не переводите сервис на этот путь без отдельной проверки безопасности, назначения владельцев и тестового запуска. Это не автоматический rollback и не переключение JSON ↔ SQLite.

## Офлайн-переиндексация истории

Только при остановленном сервере и после проверки актуальной копии метаданных:

```bash
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader \
  --reindex-media --recovery-dir /root/boosty-metadata-backup-001

sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader --audit-media
```

Переиндексация требует точного совпадения исходных JSON и SQL с резервной копией, проверяет владельцев, историю и медиа по SHA-256, обновляет SQL-индекс в транзакции. **Не меняет JSON, файлы и права доступа.** При ошибке после фиксации SQL не включайте SQLite в обслуживание пользователей; восстановите согласованный полный snapshot.

## Аварийное восстановление только SQLite Shadow

Если экспериментальный SQL-индекс повреждён, а **JSON и медиа по-прежнему в точности соответствуют** проверенной резервной копии, восстановите только `metadata.db` (после остановки сервиса):

```bash
sudo bdy stop
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader \
  --restore-sqlite-shadow --recovery-dir /root/boosty-metadata-backup-001
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader --audit-media
```

Команда работает только офлайн: проверяет SHA-256 и согласованность бэкапа, сравнивает все JSON-файлы и их наличие с сохранённым снимком, проверяет историю и медиа на диске, отклоняет незакрытый WAL/журнал и занятую сервером директорию, затем атомарно заменяет только SQL-файл. При провале проверки после замены пытается вернуть прежний SQL. Копия для восстановления должна находиться **вне** основного каталога данных (в том числе после разрешения симлинков). После успешной повторной проверки команда удаляет оставшиеся приватные временные файлы от прежних прерванных восстановлений. Сбои питания и нарушения требований файловой системы требуют полного снимка VPS; эта операция не заменяет полный rollback.

**Аварийные проверки CI:** отдельный дочерний процесс принудительно завершается реальным `SIGKILL` после записи первых 256 байт временного SQLite, после полного создания временного файла и сразу после синхронизированной подмены `metadata.db`. Тесты подтверждают неизменность JSON, отсутствие публикации неполной БД, освобождение блокировки и успешный повторный запуск восстановления. Также программно инъецируется `ENOSPC` (нехватка места) во время записи и после подмены; проверяются отказ, откат и повторное восстановление. Дополнительно CI запускает отдельный тестовый бинарник в **изолированном tmpfs 32 МиБ**: тест реально заполняет этот раздел, освобождает только один блок, получает системный `ENOSPC` при попытке копирования SQLite, проверяет неизменность JSON/старой базы и повторяет восстановление после освобождения места. Перед заполнением проверяются тип и ограниченный размер файловой системы, чтобы исключить заполнение диска хоста. Эти испытания **не заменяют** отключение питания, повреждения блочного устройства или E2E на копии реального VPS.

**Защита от изменений копии во время восстановления:** до проверки приватного снимка код фиксирует контрольную сумму и размер SQLite **из исходного манифеста**, а также SHA-256 самого манифеста. После верификации и далее после сканирования медиа, копирования и непосредственно перед атомарной подменой обе контрольные суммы сверяются с исходными. Если резервный SQL или манифест изменились, операция отказывает и не заменяет живой файл. Регрессионные тесты изменяют копию сразу после проверки (включая согласованное изменение манифеста), после аудита и после подготовки временного файла.

**Не используйте восстановление SQL Shadow**, если после создания копии появились новые архивы, изменились ACL, учётные записи, подписки или какие-либо файлы архива. Команда откажет в обнаруженных несоответствиях. Она не перезаписывает `jobs.json`, `imports.json`, `accounts.json`, `authors.json`, медиа, токены, TLS и не включает SQLite-primary.

## Экспериментальный Shadow

`BD_SQLITE_SHADOW=1` включает фоновое зеркалирование оперативных JSON-метаданных в существующую `metadata.db`. Shadow следует за успешной записью JSON, периодически повторяет сверку и сообщает ошибки по журналу и `GET /api/admin/sqlite-shadow`. По умолчанию SQL-история/медиа при этом не зеркалируются.

**Экспериментальный онлайн-индекс (отдельное согласие):** только вместе с `BD_SQLITE_SHADOW=1` можно включить `BD_SQLITE_MEDIA_SHADOW=1`. После запуска сервера фоновый процесс сверяет исторические версии и SHA-256 медиа и фиксирует `archive_revisions` + `revision_assets` в единой SQL-транзакции. Уведомления возникают при завершении загрузки, восстановлении версии, окончательном удалении и записи дополнительной версии видео. Индексирование откладывается, пока есть задачи `queued`/`running`; неуспешное индексирование не изменяет JSON или файлы и сохраняет старый SQL-индекс. При очередном проходе ошибка повторно проверяется. Дополнительные поля администратора: `mediaEnabled`, `mediaPending`, `mediaError`, `mediaLastSuccess`.

**Внимание:** для больших библиотек полный пересчёт SHA-256 может потреблять существенные дисковые ресурсы, а SQL-индекс ещё не является источником для пользовательского API. Не включайте этот режим без резервной копии VPS, свободного диска и возможности наблюдать логи. Экспериментальный режим не выполняет физическое удаление CAS, автоматическое восстановление, переключение backend или миграцию паролей/токенов. При повреждении ранее зарегистрированной текущей версии SQL-индексирование отказывает, вместо того чтобы молча удалять текущую запись.

`BD_SQLITE_VERIFY=1` и `BD_SQLITE_SHADOW=1` одновременно не включать. Перед первым включением Shadow требуется свежий экспорт и проверка SQLite. Для возвращения к обычному режиму удалите флаг и перезапустите службу; JSON не перестаёт быть основным хранилищем.

## Экспорт новых SQL-записей в отдельный JSON-снимок

Для подготовки обратного SQL-primary → JSON перехода на **остановленной** установке можно выгрузить актуальную SQL-базу в новую приватную копию, в том числе после появления новых SQL-записей, которых нет в текущем JSON:

```bash
sudo bdy stop
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader \
  --export-sqlite-json-dir /root/boosty-sql-json-recovery-001
sudo boosty-dbcheck --verify-backup-dir /root/boosty-sql-json-recovery-001
```

Создаётся новый приватный каталог с `metadata.db`, нормализованными `jobs.json` и `imports.json`, а также существующими `accounts.json` и `authors.json`, если они есть. Формат совместим с `--verify-backup-dir`. Проверяются структура SQL, индексы, владельцы, ACL, архивы и медиа по SHA-256; непустой WAL, работающий сервер и незавершённые журналы запрещены. Экспорт **не** заменяет существующий каталог и не может быть создан внутри рабочего DATA.

**Важно:** это отдельная аварийная **копия метаданных**, а не восстановление сервера или подтверждение безопасного SQL-primary. Исходные JSON, SQL, медиа и права не изменяются. В копию не входят файлы медиа, токены и внешние TLS-ключи. Чтобы восстановить работающий сервер из SQL после новых записей, всё ещё нужен отдельный транзакционный rollback с проверкой полного снимка; вручную заменять файлы JSON на работающем сервере нельзя.

## Восстановление SQL + полного архива в новый каталог (без замены сервера)

Если подготовлены **два независимых проверенных снимка** — полный каталог приложения (созданный до изменений) и более свежий экспорт SQL→JSON, — их можно объединить **исключительно в новом каталоге**. Это позволяет восстановить обновлённые задачи, импорт и выдачи доступа из SQL, сохранив медиа и локальные секреты из полного снимка:

```bash
sudo boosty-dbcheck \
  --from-full-snapshot-dir /root/boosty-data-snapshot-001 \
  --restore-sqlite-json-dir /root/boosty-sql-json-recovery-001 \
  --restore-to /root/boosty-detached-recovery-001
```

Экспорт метаданных можно создать командой `--export-sqlite-json-dir` (см. выше). Полный архив создаётся `--full-snapshot-dir`. **Каталог назначения не должен существовать** и не может быть внутри любого из исходных снимков.

Восстановление проверяет SHA-256 обоих исходников, публикует результат атомарно только после сверки SQL/JSON, владельцев, ACL, истории версий и реальных файлов медиа. Если `accounts.json` или `authors.json` изменились между снимками, операция отказывается совмещать разные эпохи учётных данных: потребуется новый согласованный полный снимок. Дополнительно проверяется монотонность заданий и импортов: если SQL не содержит уже сохранённые записи полного снимка или предлагает более старые метаданные, восстановление прекращается без публикации. Исходные каталоги не изменяются. Прерванная операция не публикует частично восстановленный каталог; после принудительного завершения процесса может остаться приватный временный каталог `.boosty-sql-recovery-*` рядом с назначением.

**Это не автоматический rollback рабочей установки.** Восстановленный каталог нельзя использовать как основное хранилище без отдельной проверки конфигурации, владельцев файлов, внешних ключей и последствий всех изменений после полного снимка. В полной копии не сохраняются конфигурация `/etc`, внешние TLS-ключи, systemd и бинарники. SQL-primary пока не включён.

## Осталось до перехода на SQLite

1. Провести нагрузочные и аварийные испытания экспериментальной онлайн-синхронизации файлового индекса и подтвердить корректность при многогигабайтных видео.
2. Реализовать контролируемое переключение read/write с резервной копией, полным восстановлением и проверкой прав.
3. Провести аварийные E2E на копии реального VPS, включая сбои питания и переполненный диск.

Пока эти пункты не выполнены, **не удаляйте JSON-файлы и не переключайте сервер на SQL вручную**.

## Строгая офлайн-проверка перед SQL cutover (не включает новый backend)

После остановки всех экземпляров сервиса и checkpoint SQLite создайте **новую** приватную резервную копию метаданных вне каталога данных, затем выполните:

```bash
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader \
  --cutover-preflight --recovery-dir /root/boosty-metadata-backup-001
```

`--cutover-preflight` откажет, если хотя бы один из пунктов не выполнен: существование и SHA-256 резервной копии, совпадение её `jobs.json`, `imports.json` и `metadata.db` с текущими файлами, а также одинаковое наличие и содержимое `accounts.json` и `authors.json`, отсутствие незавершённого журнала JSON или WAL, совпадение владельческих метаданных и ACL в SQL/JSON, валидность истории и SHA-256 реальных медиа/CAS-файлов. Команда **ничего не меняет** и не означает разрешение включить SQLite как primary backend. Она не заменяет полный снимок VPS (медиа, ключи, аккаунты, TLS), проверку восстановления и испытания отказов диска.

При экспериментальном `BD_SQLITE_MEDIA_SHADOW=1` сканирование файлов использует контекст отмены сервера; при остановке службы оно должно прерываться, а SQL-транзакция — откатываться. Индекс и физические CAS-файлы не используются для выдачи доступа пользователям.
