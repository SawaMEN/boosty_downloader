# Транзакционная модель базы для общего архива Boosty

## Состояние реализации

**Сейчас** используются `jobs.json` + `imports.json` + отдельные пользовательские каталоги, а физически одинаковые медиа экономят место через `SHA-256 + hardlink` (`internal/server/dedup.go`). Подписка сохраняется как снимок уровня в `Job.Subscription` и в личном манифесте; предыдущие версии — в `revisions/{owner}/{author}/{post}/{revision}`, до 8. **SQLite-схема, офлайн-конвертер и необязательная Go-проверка экспортированной базы реализованы. Однако SQLite НЕ используется сервером как рабочее хранилище данных.** JSON остаётся единственным источником правды. Нельзя считать миграцию завершённой.

## Предлагаемый принцип: глобальный пост, собственные доступы и единичные файлы

Три разные идентичности нельзя смешивать:

1. **Пост**: пара `author_slug + remote_post_id`. Пример: публикацию X сохранили пользователи А и Б в разные дни. Глобальная запись `source_posts` одна.
2. **Архив владельца и версия**: `owner_id + post_key`, с собственной историей, именем подписки, датой проверки и правами. Записей владельцев две, даже если видео полностью совпадают. Это не «два физических архива», а две ссылки на пользовательские данные; другая подписка не получает доступ автоматически.
3. **Физический медиаобъект**: точный `SHA-256 + size`, а не ID публикации, тариф или CDN URL. Если байты одинаковы, физический blob существует только один раз, ссылки могут быть многопользовательскими и многоверсионными.

Если владелец А подписан на уровень A, а Б на уровень Б, нельзя предполагать, что более дорогой уровень всегда включает один и тот же контент. На Boosty есть индивидуальные покупки, временные окна и изменяющиеся/скрытые уровни. Каждая новая подписка и каждый пост подтверждаются **аккаунтом владельца** через Boosty `Post.HasAccess` перед скачиванием. Доступ к прежнему архиву из общего CAS или `source_posts` сам по себе запрещён. Наличие совпадающего хеша позволяет **экономить диск после получения и проверки данных**, а не обходить проверку прав или выдавать закрытый контент другому аккаунту.

### Таблицы целевой SQLite

| Таблица | Назначение |
| --- | --- |
| `source_posts` | один канонический идентификатор удалённой публикации |
| `owner_archives` | уникальная копия на пользователя и пост, включая корзину/синхронизацию |
| `subscription_observations` | источник и время наблюдения тарифа владельца; не доказательство минимального тарифа поста |
| `archive_revisions` | неизменяемые версии, принадлежность владельцу, ссылки на факт подписки |
| `media_blobs` | точный SHA-256, размер и единственный физический путь |
| `revision_assets` | `revision_id + asset_path → sha256`; много архивов ссылаются на один объект |
| `archive_grants` | персональное разрешение для конкретного архивного объекта, не для глобального поста |
| `archive_events` | аудит изменений и очистки без хранения секретов |

Схема: [`deploy/sqlite/schema_v1.sql`](../deploy/sqlite/schema_v1.sql). Офлайн-экспорт покрывает архивы, историю версий, ACL, проверенные SHA-256, снимки уровней и JSON-метаданные импорта; **Go-SQLite-адаптер, переключение/откат режима и нагрузочные испытания остаются невыполненными.**

## Миграция без потери архива

1. Прекратить конкурентные записи или временно остановить воркеры; сделать проверяемую копию `jobs.json`, `imports.json`, ACL и существующих manifests.
2. Создать `metadata.db`, включить `foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout`, открыть `BEGIN IMMEDIATE` для миграций и зафиксировать версию схемы.
3. Для каждого `Job` создать/найти `source_posts`, связать `owner_archives` без объединения владельцев и перенести снимки подписок. Не приписывать старым записям неизвестные тарифы.
4. Инвентаризировать текущие файлы `library/` и `revisions/`, сверить SHA-256, `media_blobs` и ссылки `revision_assets`. Не считать имя файла/размер доказательством идентичности. Удерживать старые пути до окончания сверки.
5. Сверить количество архивов/версий по владельцам и тесты ACL, затем атомарно переключить режим чтения метаданных. Сохранить резервную копию с возможностью отката до изменения формата.
6. Только после проверки разрешить транзакционную очистку неиспользуемых blobs. Удалять физический blob можно лишь если нет ссылок в метаданных и на FS нет иных hardlinks. При рассогласовании — сохранить данные и сообщить администратору.

**Не делать:** раздавать архивы по одному лишь `post_id`, считать tier владельца уровнем доступа конкретного поста, сохранять токены в глобальных таблицах, выполнять полное копирование видео между подписками, принимать непроверенные CDN-хеши и удалять CAS-блок без проверки ссылок.

## Оптимизация для VPS

SQLite WAL в файловой БД снижает нагрузку и обеспечивает транзакционность без отдельного PostgreSQL. На слабом VPS предпочтительнее SQLite с одним writer-потоком и короткими транзакциями. Крупные медиа — не BLOB внутри SQLite, а файлы CAS; в БД только индексы, размеры, хеши и права. Квота пользователя считается логически по его версиям и собственным файлам; экономия физического места считается по уникальным инодам/CAS-блокам. Сложные полнотекстовые индексы и background GC включать лишь после замеров.

Текущее ограничение: две подписки на один пост не могут без сети получить друг другу защищённый контент, потому что доступ должен быть доказан отдельно. Повторный **сетевой** трафик возможен; повторный **дисковый** объём при полностью совпавших SHA-256 устраняет hardlink-дедупликация.

## Промежуточная оптимизация без включения SQLite (11.11.2026)

`ArchiveManifest.contentSha256` — отпечаток отображаемых блоков публикации, комментариев, вложений SHA-256 и приватной идентичности подписки без времени наблюдения; **это не ключ ACL и не хеш физических файлов**. Он нужен только для подавления повторных одинаковых версий при успешном обновлении. Новая версия сначала сохраняется по прежним правилам, затем сравнение выполняется после публикации; неуспешное обновление оставляет резервный снимок. Старые архивы без отпечатка не удаляются автоматически; для них первый рефреш может создать одну избыточную версию. В общих API и ZIP отпечаток скрывается, поскольку включает приватный тариф. Реальная SQLite-миграция остаётся не подключена.


## Этап 12.3.1 — безопасный офлайн-экспорт (11.11.2026)

`tools/sqlite_migrate.py` использует **только стандартную библиотеку Python 3** (`sqlite3`) и SQLite WAL, не требует CGO или драйверов Go. Это **отдельная диагностическая копия метаданных**, не рабочая база. Программа ничего не изменяет в `jobs.json`, `imports.json`, `library/`, `revisions/`, `blobs/`, `vault/` и пользовательских правах.

**Обязательно остановить сервер и фоновые обновления перед запуском**: алгоритм проверяет повторные SHA-256 файлов метаданных и отсутствие изменений у каждого медиафайла во время чтения, но не может гарантировать согласованный снимок при параллельной записи другого процесса. Рекомендуется предварительно сделать резервную копию каталога данных.

Пример для каталога `/var/lib/boosty-downloader` (заменить реальным `BD_DATA_DIR`):

```bash
sudo systemctl stop boosty-downloader
python3 tools/sqlite_migrate.py --data-dir /var/lib/boosty-downloader
python3 tools/sqlite_migrate.py --data-dir /var/lib/boosty-downloader --output /var/lib/boosty-downloader/metadata-preview.db
sudo systemctl start boosty-downloader
```

Первая команда Python только проверяет в памяти и выводит числа архивов, версий, импортов, разрешений и вложений, а также объёмы логически представленных файлов и уникальных инодов вложений. Вторая создаёт **новую** SQLite-базу; уже существующий путь никогда не перезаписывается. Доступ к файлу БД устанавливается `0600`. Поскольку это снимок, Go-сервер **не читает** `metadata-preview.db`: после последующих загрузок он устареет.

Скрипт работает потоково для крупных медиа (буфер 1 МиБ, не загружает видео целиком в память), сверяет каждый файл с `manifest.json` по размеру и SHA-256, валидирует пути без символических ссылок, сохраняет изоляцию `owner_id` и разрешения только на конкретный `archive_id`. У одного исходного поста может быть несколько независимых архивов владельцев и один логический SHA-256 медиа. Если CAS-дедупликация не включена, `media_blobs.relative_path IS NULL`: это означает наличие **контентного индекса**, но не единственный физический inode. Неизвестные/повреждённые файлы останавливают экспорт, вместо того чтобы silently потерять данные.

В `owner_archives.payload_json` и `author_imports.payload_json` хранится исходный JSON целиком для будущей точной сверки и обратимой миграции. Файлы токенов Boosty, парольные хеши и ключи шифрования не копируются. Оригинальные каталоги остаются нетронутыми; откат от диагностического экспорта — удаление новой БД после проверки. Никаких операций garbage collection или переключения рабочих read/write-маршрутов сейчас нет.

Проверки: `python3 -m unittest discover -s tests -p 'test_sqlite_migrate.py' -v`, затем GitHub Actions. Проверяются совпадающие медиа двух владельцев, изолированные ACL, импорты, история, отсутствие права на перезапись, отказ при расхождении SHA-256, небезопасных путях и симлинках.

**Статус:** подэтап офлайн-экспорта — 4 из 5 контрольных задач выполнены в коде и локальных тестах; осталась проверка GitHub CI и испытание на остановленном реальном VPS. Основной этап 12.3 пока не закончен: следующий крупный шаг — встраивание SQLite-драйвера в Go, переключение с JSON с healthcheck/rollback и реальные замеры. 

## Этап 12.3.2 — Go read-only preflight

Добавлен Go-драйвер SQLite (чистый Go, без CGO) и сравнение экспортированной базы с действующими JSON-файлами перед потенциальным переключением. Для полного контроля необходимо использовать **новый** экземпляр снимка после остановки службы:

```bash
sudo systemctl stop boosty-downloader
python3 tools/sqlite_migrate.py --data-dir /var/lib/boosty-downloader --output /var/lib/boosty-downloader/metadata.db
go run ./cmd/boosty-dbcheck --data-dir /var/lib/boosty-downloader
sudo systemctl start boosty-downloader
```

Если `metadata.db` уже существует, конвертер намеренно откажется от перезаписи; для нового запуска выбрать другой пустой тестовый каталог или после резервного копирования вручную убрать **только** прежнюю диагностическую SQLite-копию. Переименование SQLite не должно изменять путь `jobs.json` и `imports.json`.

Go-проверка открывает SQLite в `mode=ro`, сравнивает структуры владельца/поста, полный JSON архивов и импортов, проверяет ACL-гранты и числа строк, `integrity_check`, `foreign_key_check`, идентичность версии схемы и неизменность исходных файлов за время проверки. Доступ к прежним версиям и медиабайтам по глобальному `source_post` **не разрешается**: HTTP всё ещё использует персональные проверки JSON.

Дополнительно при отладке допустим запуск `BD_SQLITE_VERIFY=1` в окружении Go-сервера. Эта проверка срабатывает **до** выполнения legacy-миграций JSON и старта воркеров; если данные не совпадают, процесс не стартует. Для обычного production-режима переменную оставлять не нужно: активные загрузки неизбежно сделают диагностический SQLite-снимок устаревшим, и проверка на следующем старте откажет до нового экспорта. Это не механизм фоновой синхронизации SQL.

**Откат после неуспешного preflight:** не включать SQLite; убрать `BD_SQLITE_VERIFY`, если задавали его, и запустить обычную службу с прежними JSON. Файлы JSON, личные ACL, медиа и приватные ключи инструментами проверки не изменяются. Полноценное переключение read/write backend, журналирование транзакций и crash-safe rollback ещё не реализованы.

## Этап 12.3.3 — транзакционный SQLite-репозиторий (экспериментальный, 11.11.2026)

`internal/server/sqlite_metadata.go` реализует изолированный Go-репозиторий, который работает с копией уже мигрированной `metadata.db` через `mode=rw`. Он не вызывает `New(Storage)` и **не активирован в HTTP, планировщике, импорте или скачивании**. Поэтому текущие данные пользователей остаются в JSON.

`apply` использует одну транзакцию `database/sql` для произвольного набора записей `owner_archives`, `source_posts`, `archive_grants`, `archive_events`, `author_imports`. Прежний JSON каждой обновляемой записи выступает версией для compare-and-swap: если между чтением и записью данные изменились или ID уже занят, возвращается ошибка, а вся транзакция откатывается. Не допускаются изменение владельца и идентичности поста, перенос грантов другому владельцу, неподтверждённые имена путей или дубли разрешений. Прочитать один архив/импорт можно только с указанием его собственного `owner_id`.

**Безопасная граница:** SQL-транзакция защищает **метаданные**, но не может атомарно фиксировать изменения `library/`, `revisions/`, CAS hardlinks и JSON. Кроме того, SQLite-индекс исторических версий пока не обновляется из реальных файловых операций. Потому автоматическое отключение JSON, двусторонняя синхронизация, SQL-авторизация HTTP и GC отключены до появления единого журнала операций, отката и проверенных тестов аварий. Проверка API/ACL прежних собственников по-прежнему использует существующее `Storage`.

Тесты: `go test -race ./internal/server -run 'TestSQLiteMetadata|TestSQLitePreflight' -count=1`. Для реального VPS сначала необходим изолированный архивный snapshot и тестовый экспорт; пробовать изменения непосредственно на работающем `metadata.db` до полноценного cutover запрещено.


## Этап 12.3.4 — аварийно-безопасный мост и подготовка к переключению (12.11.2026)

Для операции изменения расписания импорта вместе с флагами заданий внедрена транзакция двух JSON-файлов `jobs.json` и `imports.json`. Прежде чем заменить файлы, сервер записывает приватный `.metadata-transaction.json` с прежним и будущим содержимым, версиями и SHA-256 и синхронизирует запись на диск. После обоих переименований сохраняется фаза `committed`. При следующем запуске фаза `prepared` **откатывает оба файла**, а фаза `committed` **повторно применяет оба файла**. Операция идемпотентна; повреждение/симлинк журнала не игнорируется и прерывает запуск до вмешательства оператора. До восстановления журнала включать проверку SQLite или фоновые задачи нельзя.

**Предварительный снимок метаданных** выполняется только после остановки службы и создания *свежей* проверенной `metadata.db` через офлайн-экспорт:

```bash
sudo systemctl stop boosty-downloader
python3 tools/sqlite_migrate.py --data-dir /var/lib/boosty-downloader --output /var/lib/boosty-downloader/metadata.db
go run ./cmd/boosty-dbcheck --data-dir /var/lib/boosty-downloader --backup-dir /root/boosty-sqlite-backup-001
```

Для подготовки нужен новый каталог `--backup-dir` **вне** каталога данных; если указанная БД или каталог резервной копии уже существует, сначала вручную выбрать другой новый путь, ничего не перезаписывать. Снимок содержит `jobs.json`, `imports.json`, `metadata.db`, а при наличии — `authors.json`, `accounts.json`; `backup-manifest.json` содержит SHA-256 и размеры. Каталог имеет режим `0700`, файлы `0600`, что необходимо, поскольку `accounts.json` содержит чувствительные сведения. При любом несоответствии снимок не публикуется.

**Ограничение:** это **копия только метаданных**, не полный бэкап VPS. Для настоящего восстановления обязательно сделать согласованную файловую копию `library/`, `revisions/`, `blobs/`, `vault/`, настроек и ключа шифрования, не меняя права и hardlinks. Инструмент отказывает, если база имеет незавершённый WAL: сырое копирование `metadata.db` без непустого WAL было бы повреждённым. Он не пытается автоматически чинить БД и не включает SQLite как основной backend.

Если при запуске найден журнал, не удалять его вручную: он указывает, какую из двух согласованных версий нужно восстановить. При ошибке контрольной суммы остановиться и восстановить весь согласованный снимок, не отдельный JSON-файл. До готового SQL-cutover **возврат к JSON остаётся нормальным режимом сервера**, а ручной импорт бэкапа в активную систему может удалить новые данные; автоматический restore-backend пока не реализован.

### Опциональный SQLite Shadow (этап 12.3.4)

Отдельный режим зеркалирования метаданных включается только переменной окружения `BD_SQLITE_SHADOW=1`. По умолчанию выключен. Предварительно **остановите** сервер, сделайте полный снимок VPS и свежий экспорт SQLite схемы v1 в `<BD_DATA_DIR>/metadata.db`. Убедитесь, что файл принадлежит системному пользователю службы и доступен для записи. Не включайте одновременно `BD_SQLITE_VERIFY=1`: старый режим сверяет всю историческую структуру, а shadow обновляет только оперативные метаданные.

Для установленного native/systemd и Docker Compose переменные читаются из `/etc/boosty-downloader/environment`. После подготовки базы добавьте в этот файл:

```text
BD_SQLITE_SHADOW=1
```

Запустите службу. На старте Go проверит существующий SQLite-файл, версию схемы и отсутствие противоречащих приватному payload SQL-грантов. Затем в фоне (после изменения JSON и дополнительно раз в 30 секунд) зеркалируются `owner_archives`, `source_posts`, `archive_grants`, `archive_events`, `author_imports` одной SQL-транзакцией. Состояние доступно администратору по `GET /api/admin/sqlite-shadow`: `enabled`, `status`, `lastSuccess`, `lastAttempt`, `lastError`, `authoritative=json`. При ошибке SQLite записи JSON не теряются и остаются авторитетными; механизм повторяет попытки и фиксирует ошибки в логах. При несовместимом SQL или отсутствии файла режим не запускается, без автоматического создания пустой БД. При отключении переменной сервер возвращается к обычному JSON-режиму, поскольку SQLite не участвует в HTTP-проверке прав.

**Не является миграцией всей системы:** `archive_revisions`, `revision_assets`, `media_blobs` и физические файлы/защищённые токены/аккаунты пока не реплицируются. SQL-данные нельзя использовать для обслуживания клиентов, восстановления файлов, GC или переключения backend без отдельной процедуры полной миграции. Схема рассчитана на один пишущий процесс сервера в каталоге данных; несколько одновременно работающих экземпляров не поддерживаются. Реальное переключение JSON на SQL будет отдельным этапом с журналом cutover, полным снапшотом файлов и откатом.

### Глубокая офлайн-проверка архива и проверка резервной копии

После остановки всех процессов записи и проверки/закрытия SQLite WAL:

```bash
go run ./cmd/boosty-dbcheck --data-dir /var/lib/boosty-downloader --audit-media
go run ./cmd/boosty-dbcheck --verify-backup-dir /root/boosty-sqlite-backup-001
```

`--audit-media` не изменяет БД или медиа и требует **полного каталога данных**. Проверяются `PRAGMA integrity_check`, `foreign_key_check`, принадлежность текущих и исторических версий архивов, реальные файлы, манифесты, SHA-256 всех включённых медиа, наличие осиротевших каталогов архива вне SQL-индекса и заявленные CAS-файлы в `blobs/sha256/...`. Симлинки и неканонические пути запрещены. Для гарантированно неизменяемого чтения аудитор использует `immutable=1`, поэтому перед запуском отклоняет непустой `metadata.db-wal`; прежде необходимо безопасно завершить службу и checkpoint SQLite. Отсутствие ошибок не является тестом внезапного выключения питания.

`--verify-backup-dir` работает только с каталогом, созданным `--backup-dir`, и **не** требует оригинальной медиатеки: сверяются размер и SHA-256 файлов, список/версия манифеста, приватность каталога и файлов, целостность SQL, индексируемые поля и ACL каждой записи по копиям `jobs.json` и `imports.json`. SQL читается без записи через `mode=ro&immutable=1`; контрольная сумма SQLite вычисляется потоково без загрузки БД целиком. Это проверка **метаданных**, а не копия и не восстановление видео или исходных файлов. Путь `--verify-backup-dir` не совмещается с `--data-dir`.

В ходе подготовки дополнительно устранены гонка нескольких параллельных shadow-проходов (одновременно фиксируется только один снимок) и ошибки in-memory отката `upsert` / `updateImport`: если атомарная запись JSON завершилась ошибкой, несохранённая запись не должна оставаться изменённой в памяти.
