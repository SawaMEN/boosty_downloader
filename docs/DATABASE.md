# Транзакционная модель базы для общего архива Boosty

## Состояние реализации

**Сейчас** используются `jobs.json` + `imports.json` + отдельные пользовательские каталоги, а физически одинаковые медиа экономят место через `SHA-256 + hardlink` (`internal/server/dedup.go`). Подписка сохраняется как снимок уровня в `Job.Subscription` и в личном манифесте; предыдущие версии — в `revisions/{owner}/{author}/{post}/{revision}`, до 8. **SQLite-схема `deploy/sqlite/schema_v1.sql` пока проектная и НЕ подключена к приложению.** Нельзя считать миграцию завершённой.

## Предлагаемый принцип: глобальный пост, собственные доступы и единичные файлы

Три разные идентичности нельзя смешивать:

1. **Пост**: пара `author_slug + remote_post_id`. Пример: публикацию X сохранили пользователи А и Б в разные дни. Глобальная запись `source_posts` одна.
2. **Архив владельца и версия**: `owner_id + post_key`, с собственной историей, именем подписки, датой проверки и правами. Записей владельцев две, даже если видео полностью совпадают. Это не «два физических архива», а две ссылки на пользовательские данные; другая подписка не получает доступ автоматически.
3. **Физический медиаобъект**: точный `SHA-256 + size`, а не ID публикации, тариф или CDN URL. Если байты одинаковы, физический blob существует только один раз, ссылки могут быть многопользовательскими и многоверсионными.

Если владелец А подписан на уровень A, а Б на уровень Б, нельзя предполагать, что более дорогой уровень всегда включает один и тот же контент. На Boosty есть индивидуальные покупки, временные окна и изменяющиеся/скрытые уровни. Каждая новая подписка и каждый пост подтверждаются **аккаунтом владельца** через Boosty `Post.HasAccess` перед скачиванием. Доступ к прежнему архиву из общего CAS или `source_posts` сам по себе запрещён. Наличие совпадающего хеша позволяет **экономить диск после получения и проверки данных**, а не обходить проверку прав или выдавать закрытый контент другому аккаунту.

### Таблицы целевой SQLite

| Таблица | Назначение |
| --- | --- |
| `source_posts` | один канонический идентификатор удалённой публикации |
| `owner_archives` | уникальная копия на пользователя и пост, включая корзину/синхронизацию |
| `subscription_observations` | источник и время наблюдения тарифа владельца; не доказательство минимального тарифа поста |
| `archive_revisions` | неизменяемые версии, принадлежность владельцу, ссылки на факт подписки |
| `media_blobs` | точный SHA-256, размер и единственный физический путь |
| `revision_assets` | `revision_id + asset_path → sha256`; много архивов ссылаются на один объект |
| `archive_grants` | персональное разрешение для конкретного архивного объекта, не для глобального поста |
| `archive_events` | аудит изменений и очистки без хранения секретов |

Схема: [`deploy/sqlite/schema_v1.sql`](../deploy/sqlite/schema_v1.sql). Она проектирует уникальность и индексы, но настоящий Go-SQLite-адаптер, двусторонняя миграция и нагрузочное тестирование остаются отдельным этапом.

## Миграция без потери архива

1. Прекратить конкурентные записи или временно остановить воркеры; сделать проверяемую копию `jobs.json`, `imports.json`, ACL и существующих manifests.
2. Создать `metadata.db`, включить `foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout`, открыть `BEGIN IMMEDIATE` для миграций и зафиксировать версию схемы.
3. Для каждого `Job` создать/найти `source_posts`, связать `owner_archives` без объединения владельцев и перенести снимки подписок. Не приписывать старым записям неизвестные тарифы.
4. Инвентаризировать текущие файлы `library/` и `revisions/`, сверить SHA-256, `media_blobs` и ссылки `revision_assets`. Не считать имя файла/размер доказательством идентичности. Удерживать старые пути до окончания сверки.
5. Сверить количество архивов/версий по владельцам и тесты ACL, затем атомарно переключить режим чтения метаданных. Сохранить резервную копию с возможностью отката до изменения формата.
6. Только после проверки разрешить транзакционную очистку неиспользуемых blobs. Удалять физический blob можно лишь если нет ссылок в метаданных и на FS нет иных hardlinks. При рассогласовании — сохранить данные и сообщить администратору.

**Не делать:** раздавать архивы по одному лишь `post_id`, считать tier владельца уровнем доступа конкретного поста, сохранять токены в глобальных таблицах, выполнять полное копирование видео между подписками, принимать непроверенные CDN-хеши и удалять CAS-блок без проверки ссылок.

## Оптимизация для VPS

SQLite WAL в файловой БД снижает нагрузку и обеспечивает транзакционность без отдельного PostgreSQL. На слабом VPS предпочтительнее SQLite с одним writer-потоком и короткими транзакциями. Крупные медиа — не BLOB внутри SQLite, а файлы CAS; в БД только индексы, размеры, хеши и права. Квота пользователя считается логически по его версиям и собственным файлам; экономия физического места считается по уникальным инодам/CAS-блокам. Сложные полнотекстовые индексы и background GC включать лишь после замеров.

Текущее ограничение: две подписки на один пост не могут без сети получить друг другу защищённый контент, потому что доступ должен быть доказан отдельно. Повторный **сетевой** трафик возможен; повторный **дисковый** объём при полностью совпавших SHA-256 устраняет hardlink-дедупликация.

## Промежуточная оптимизация без включения SQLite (11.11.2026)

`ArchiveManifest.contentSha256` — отпечаток отображаемых блоков публикации, комментариев, вложений SHA-256 и приватной идентичности подписки без времени наблюдения; **это не ключ ACL и не хеш физических файлов**. Он нужен только для подавления повторных одинаковых версий при успешном обновлении. Новая версия сначала сохраняется по прежним правилам, затем сравнение выполняется после публикации; неуспешное обновление оставляет резервный снимок. Старые архивы без отпечатка не удаляются автоматически; для них первый рефреш может создать одну избыточную версию. В общих API и ZIP отпечаток скрывается, поскольку включает приватный тариф. Реальная SQLite-миграция остаётся не подключена.
