# SQLite: текущий статус и безопасные операции

**Основное хранилище сервера — JSON.** `jobs.json` и `imports.json` управляют заданиями и импортом, `accounts.json` — пользователями. SQLite **не** используется для принятия решений о правах или выдаче файлов.

SQLite v1 используется для офлайн-экспорта, проверки, экспериментального Shadow и переиндексации истории. **Автоматическое production-переключение и откат SQLite ↔ JSON пока не реализованы.**

## Главное правило

Каждый архив принадлежит своему пользователю. Общий оригинальный пост и одинаковый SHA-256 медиа не дают другому пользователю права читать архив. Доступ к Boosty всегда определяется правами конкретного аккаунта. SQLite хранит метаданные; большие файлы остаются на диске.

## Где что находится

- `/var/lib/boosty-downloader/jobs.json`, `imports.json` — рабочие JSON.
- `library/<owner>/<author>/<post>/` — текущая версия архива.
- `revisions/<owner>/<author>/<post>/<revision>/` — исторические версии.
- `blobs/sha256/<2>/<digest>` — дедуплицированные файлы.
- `metadata.db` — необязательная SQLite схемы v1.

Схема: [schema_v1.sql](../deploy/sqlite/schema_v1.sql).

При Native утилита `boosty-dbcheck` устанавливается вместе с сервером. Для Docker скачайте одноимённый бинарник своей архитектуры из GitHub Releases и проверьте его SHA-256, либо соберите `go build ./cmd/boosty-dbcheck` из исходников и запускайте на хосте. Docker-образ не получает root-доступ к хосту.

## Безопасная офлайн-проверка

**Перед началом остановите сервис и все фоновые процессы записи, сделайте полную копию `/etc/boosty-downloader/` и `/var/lib/boosty-downloader/`.** Не выполняйте операции на изменяющихся архивных файлах. Если используется Docker, остановите контейнер через `sudo bdy stop`.

Из корня репозитория:

```bash
sudo bdy stop

# Новый путь metadata.db должен отсутствовать.
sudo python3 tools/sqlite_migrate.py \
  --data-dir /var/lib/boosty-downloader \
  --output /var/lib/boosty-downloader/metadata.db

# В Native используется boosty-dbcheck, установленный вместе с сервером.
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader

sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader --audit-media
```

`--audit-media` проверяет внешние ключи, индексы версий, манифесты, пути владельцев, CAS и SHA-256 реальных файлов. Не исправляет и не удаляет данные. Если есть **непустой WAL**, аудит откажется работать: нужно корректно закрыть SQLite и выполнить checkpoint, а не удалять WAL вручную.

## Проверенная копия метаданных

```bash
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader \
  --backup-dir /root/boosty-metadata-backup-001

sudo boosty-dbcheck \
  --verify-backup-dir /root/boosty-metadata-backup-001
```

Каталог `--backup-dir` должен быть **новым** и находиться вне основного каталога данных. Проверяются SHA-256, JSON, схема SQL, владельцы и ACL. Копия содержит **только метаданные** — это не резервная копия медиа, токенов, TLS-ключей или всего VPS.

## Офлайн-переиндексация истории

Только при остановленном сервере и после проверки актуальной копии метаданных:

```bash
sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader \
  --reindex-media --recovery-dir /root/boosty-metadata-backup-001

sudo boosty-dbcheck \
  --data-dir /var/lib/boosty-downloader --audit-media
```

Переиндексация требует точного совпадения исходных JSON и SQL с резервной копией, проверяет владельцев, историю и медиа по SHA-256, обновляет SQL-индекс в транзакции. **Не меняет JSON, файлы и права доступа.** При ошибке после фиксации SQL не включайте SQLite в обслуживание пользователей; восстановите согласованный полный snapshot.

## Экспериментальный Shadow

`BD_SQLITE_SHADOW=1` включает фоновое зеркалирование оперативных JSON-метаданных в существующую `metadata.db`. Shadow следует за успешной записью JSON, периодически повторяет сверку и сообщает ошибки по журналу и `GET /api/admin/sqlite-shadow`. По умолчанию SQL-история/медиа при этом не зеркалируются.

**Экспериментальный онлайн-индекс (отдельное согласие):** только вместе с `BD_SQLITE_SHADOW=1` можно включить `BD_SQLITE_MEDIA_SHADOW=1`. После запуска сервера фоновый процесс сверяет исторические версии и SHA-256 медиа и фиксирует `archive_revisions` + `revision_assets` в единой SQL-транзакции. Уведомления возникают при завершении загрузки, восстановлении версии, окончательном удалении и записи дополнительной версии видео. Индексирование откладывается, пока есть задачи `queued`/`running`; неуспешное индексирование не изменяет JSON или файлы и сохраняет старый SQL-индекс. При очередном проходе ошибка повторно проверяется. Дополнительные поля администратора: `mediaEnabled`, `mediaPending`, `mediaError`, `mediaLastSuccess`.

**Внимание:** для больших библиотек полный пересчёт SHA-256 может потреблять существенные дисковые ресурсы, а SQL-индекс ещё не является источником для пользовательского API. Не включайте этот режим без резервной копии VPS, свободного диска и возможности наблюдать логи. Экспериментальный режим не выполняет физическое удаление CAS, автоматическое восстановление, переключение backend или миграцию паролей/токенов. При повреждении ранее зарегистрированной текущей версии SQL-индексирование отказывает, вместо того чтобы молча удалять текущую запись.

`BD_SQLITE_VERIFY=1` и `BD_SQLITE_SHADOW=1` одновременно не включать. Перед первым включением Shadow требуется свежий экспорт и проверка SQLite. Для возвращения к обычному режиму удалите флаг и перезапустите службу; JSON не перестаёт быть основным хранилищем.

## Осталось до перехода на SQLite

1. Провести нагрузочные и аварийные испытания экспериментальной онлайн-синхронизации файлового индекса и подтвердить корректность при многогигабайтных видео.
2. Реализовать контролируемое переключение read/write с резервной копией, полным восстановлением и проверкой прав.
3. Провести аварийные E2E на копии реального VPS, включая сбои питания и переполненный диск.

Пока эти пункты не выполнены, **не удаляйте JSON-файлы и не переключайте сервер на SQL вручную**.

## Строгая офлайн-проверка перед SQL cutover (не включает новый backend)

После остановки всех экземпляров сервиса и checkpoint SQLite создайте **новую** приватную резервную копию метаданных вне каталога данных, затем выполните:

```bash
sudo boosty-dbcheck --data-dir /var/lib/boosty-downloader \
  --cutover-preflight --recovery-dir /root/boosty-metadata-backup-001
```

`--cutover-preflight` откажет, если хотя бы один из пунктов не выполнен: существование и SHA-256 резервной копии, совпадение её `jobs.json`, `imports.json` и `metadata.db` с текущими файлами, отсутствие незавершённого журнала JSON или WAL, совпадение владельческих метаданных и ACL в SQL/JSON, валидность истории и SHA-256 реальных медиа/CAS-файлов. Команда **ничего не меняет** и не означает разрешение включить SQLite как primary backend. Она не заменяет полный снимок VPS (медиа, ключи, аккаунты, TLS), проверку восстановления и испытания отказов диска.

При экспериментальном `BD_SQLITE_MEDIA_SHADOW=1` сканирование файлов использует контекст отмены сервера; при остановке службы оно должно прерываться, а SQL-транзакция — откатываться. Индекс и физические CAS-файлы не используются для выдачи доступа пользователям.
